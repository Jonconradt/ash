Démarrage

De quoi ai-je besoin avant de pouvoir utiliser ash ?

Vous avez besoin de l'exécutable ash, d'un point de terminaison IA et d'un nom de modèle. L'exécution de ash install les configure automatiquement : il utilise une clé API de fournisseur de cloud déjà définie ou un serveur d'inférence local en cours d'exécution lorsqu'il est trouvé, sinon il affiche un menu de fournisseur numéroté et demande une clé API, puis vous permet de choisir un modèle dans la liste des modèles du point de terminaison. Vous pouvez également définir AI_ENDPOINT et AI_MODEL manuellement. Un point de terminaison local tel qu'Ollama peut utiliser http://localhost:11434, et un hôte LAN comme http://brain.local:11434 ou une IP privée est également traité comme local (sauf si ASH_STRICT=1) ; les points de terminaison du cloud doivent utiliser HTTPS et nécessitent également AI_AUTH_TOKEN. L'intégration du shell est facultative : vous pouvez toujours exécuter ash "your question" directement.

Où ash s'installe-t-il et comment puis-je vérifier que mon shell peut le trouver ?

L'installateur vérifié place ash dans ~/.local/bin/ash, et ash install ajoute ce répertoire à votre PATH via le fichier géré ~/.ash/.ash_env. Ouvrez un nouveau terminal, puis exécutez command -v ash pour confirmer. Le programme de mise à jour automatique installe son binaire de remplacement au même emplacement ~/.local/bin/ash.

Comment utiliser ash sans changer de shell ?

Passez directement une invite citée : ash "how do I find large files?". Sans argument, ash accepte également une invite de saisie standard non interactive, telle que git diff | ash. L'utilisation directe est l'option la moins surprenante lorsque vous apprenez ash ou écrivez un script.

Pourquoi ash indique-t-il que ma configuration IA est incomplète ?

Vérifiez que AI_ENDPOINT et AI_MODEL ne sont pas vides dans l'environnement où ash s'exécute. Pour un nom d'hôte cloud, définissez également AI_AUTH_TOKEN. Exécutez printf '%s\n' "$AI_ENDPOINT" "$AI_MODEL" pour confirmer que les deux premières valeurs sont présentes, mais n'imprimez pas de jeton d'authentification dans un enregistrement de terminal ou un journal partagé.

Installation et mise à jour

ash fonctionne-t-il sous Windows 11 ?

Pas nativement. ash prend en charge bash, zsh et Fish sur macOS, Linux et FreeBSD ; il n’y a pas de cible d’installation PowerShell. Utilisez WSL pour l'expérience Linux prise en charge.

Comment installer ash dans le sous-système Windows pour Linux (WSL) ?

Installez-le dans votre distribution WSL en tant que Linux : curl -fsSL https://jonconradt.github.io/ash/install.sh | sh. Configurez ensuite AI_ENDPOINT et AI_MODEL, et exécutez ash install pour le shell exécuté dans WSL.

Comment mettre à jour ash vers la dernière version ?

Exécutez ash update sur macOS, Linux ou FreeBSD. Il télécharge la dernière archive correspondante stable, vérifie le manifeste de version avec son bundle Sigstore et le résumé SHA-256, puis s'installe sur ~/.local/bin/ash. Si la vérification de la signature échoue ou si l'archive contient des entrées non prises en charge, une confirmation interactive est requise ; n'approuvez pas une signature échouée à moins que vous ne fassiez confiance de manière indépendante à la source de la version. Les charges utiles non prises en charge sont ignorées et les exécutions non interactives refusent ces exceptions. Utilisez ash update --version vX.Y.Z pour une version spécifique ; utilisez --yes uniquement lorsque vous souhaitez remplacer les fichiers gérés personnalisés.

J'ai exécuté ash install. Pourquoi rien ne change dans ce terminal ?

L'installation met à jour un fichier de démarrage ; il ne réécrit pas le processus shell déjà en cours d'exécution. Ouvrez un nouveau terminal ou rechargez le fichier pour votre shell : source ~/.bashrc pour Bash, source ~/.zshrc pour zsh ou source ~/.config/fish/config.fish pour Fish, sauf si vous utilisez un XDG_CONFIG_HOME personnalisé.

Les commandes inconnues indiquent toujours « introuvable ». Comment puis-je dépanner l'intégration du shell ?

Première exécution de command -v ash ; le wrapper ne peut pas invoquer un binaire que votre shell ne peut pas trouver. Rechargez ou redémarrez ensuite le shell et vérifiez que son fichier de démarrage contient le bloc géré >>> ash install >>>. Enfin, exécutez ash snooze off, car une répétition laisse intentionnellement des commandes inconnues comme des échecs normaux « non trouvés ».

Quels fichiers ash install change et puis-je en avoir un aperçu ?

Il ajoute ou met à jour un bloc marqué ash dans le fichier de démarrage du shell sélectionné et gère les fichiers sous ~/.ash, y compris la configuration, des wrappers et des outils groupés. Exécutez ash install --shell bash --dry-run pour prévisualiser la modification du fichier de démarrage sans l'écrire. La réexécution de l'installation est idempotente ; utilisez --overwrite uniquement lorsque vous souhaitez actualiser les fichiers d'amorçage gérés.

ash prend-il en charge Fish ?

Oui. Exécutez ash install --shell fish. ash ajoute un bloc géré à $XDG_CONFIG_HOME/fish/config.fish, ou ~/.config/fish/config.fish lorsque XDG_CONFIG_HOME n'est pas défini. Fish utilise fish_command_not_found, donc une commande non résolue atteint ash avec ses arguments d'origine.

Pourquoi ne pas mettre en minuscules test et type dans Fish ?

Fish réserve ces noms minuscules comme éléments intégrés essentiels et ne permet pas à une fonction de les remplacer. Utilisez Test ... ou Type ... pour exprimer l'intention ash, ou invoquez directement ash "...". D'autres wrappers de collision compatibles restent disponibles.

Qu'en est-il de ksh93 ?

ksh93 n'est pas pris en charge pour l'intégration du shell. Son comportement FPATH ne peut charger qu'un fichier nommé d'après une commande inconnue ; il n'a pas de rappel générique de commande introuvable qui puisse implémenter en toute sécurité le routage d'invite ash ou le cycle de vie du courtier.

IA et connexions

ash inclut-il l'IA ?

Non. ash est un client pour un point de terminaison AI que vous configurez. Réglez AI_ENDPOINT et AI_MODEL ; ash prend en charge Ollama local et d'autres serveurs locaux compatibles OpenAI (LM Studio, llama.cpp, MLX, LocalAI, vLLM, text-Generation-webui, Jan, GPT4All) et détecte les adaptateurs de fournisseur cloud pris en charge à partir du point de terminaison, avec un remplacement facultatif AI_PROVIDER.

Que sont les serveurs MCP et comment puis-je les ajouter un ?

Les serveurs MCP (Model Context Protocol) exposent des outils qu'un modèle d'IA peut appeler, tels que la recherche, l'analyse ou des actions spécifiques à un service. Pour ajouter un serveur HTTP MCP Streamable distant, placez son URL sur sa propre ligne dans ~/.ash/.ash_allow, puis exécutez à nouveau ash. Par exemple : https://mcpplaygroundonline.com/mcp-complex-server. Ash se connecte via son courtier et propose les outils du serveur au modèle. Utilisez uniquement des serveurs en qui vous avez confiance : leurs outils peuvent effectuer des actions en votre nom. HTTPS est requis sauf pour les serveurs de développement localhost. Les fichiers ~/.ash/mcp.json existants ne sont plus lus ; déplacez leurs URL dans .ash_allow. Si l'initialisation de MCP échoue, ash continue sans outils MCP distants : il avertit dans les sessions interactives et reste silencieux dans les sessions non interactives.

Les tâches planifiées peuvent-elles utiliser des serveurs MCP ?

Non. Les tâches planifiées et autres tâches non interactives n'héritent pas du courtier d'un shell interactif, les outils MCP distants ne sont donc pas disponibles. Ash exécute toujours l'invite sans outils MCP et supprime cet échec d'initialisation attendu. Une invite qui s'appuie sur MCP peut donc se terminer sans les données ou l'action demandée. Ne planifiez pas d'invites nécessitant MCP.

MCP fonctionne-t-il lorsque ASH_STRICT=1 ?

Oui. Une ligne URL HTTP(S) enregistre explicitement un serveur MCP et n'est pas traitée comme un exécutable shell. Le mode strict ne désactive pas les serveurs MCP configurés. Il applique toujours les protections de sortie non fiables de Ash au contenu de l'outil renvoyé.

Comment fonctionne MCP OAuth et où sont stockées les informations d'identification ?

Pour un serveur protégé par OAuth, Ash ouvre la page d'autorisation dans le navigateur de bureau lorsqu'une interface graphique est disponible ; s'il ne peut pas ouvrir un navigateur, il imprime une URL à autoriser manuellement dans un navigateur sur le même hôte. Utilisez ash mcp add <url> --no-browser pour toujours utiliser le flux du terminal. Pour les connexions OAuth directes, la découverte autorise les adresses IP non publiques uniquement pour l'autorité MCP enregistrée exacte ; les autres hôtes OAuth restent soumis au blocage des adresses non publiques. Un proxy de sortie configuré est chargé de filtrer ses adresses de destination. Le courtier gère le rappel, l'échange de jetons, l'actualisation et la session MCP persistante. Les informations d'identification sont stockées dans le gestionnaire d'informations d'identification du système d'exploitation lorsqu'elles sont disponibles. S'il n'est pas disponible, configurez la solution de secours du fichier crypté à l'aide d'un ASH_MCP_CREDENTIAL_KEY aléatoire de 32 octets ; Ash ne stocke jamais la clé elle-même.

Où puis-je trouver AUTH_KEY pour les fournisseurs d'IA cloud les plus populaires ?

ash appelle cette valeur AI_AUTH_TOKEN ; il ne crée ni ne distribue de clés de fournisseur. Créez une clé dans votre compte de fournisseur, telle que OpenAI, Anthropic, Google AI Studio, Azure OpenAI, Mistral, Cohere, Groq, xAI, DeepSeek, Ensemble AI, OpenRouter, HuggingFace, ou Ollama, puis exportez-le en tant que variable d'environnement du fournisseur (ou AI_AUTH_TOKEN directement). ash install détecte automatiquement la plupart de ces variables d'environnement spécifiques au fournisseur. Les points de terminaison du cloud doivent utiliser HTTPS et nécessiter un jeton ; Les adresses privées/LAN et les noms d'hôtes .local ne sont pas traités comme des points de terminaison du cloud à moins que ASH_STRICT=1 ne soit défini.

ash ouvre-t-il une nouvelle connexion à chaque fois ?

Pas pour une utilisation normale du shell Unix interactif. Bash, zsh et Fish démarrent un courtier par session shell, communiquent avec lui via un socket Unix privé et réutilisent son pool de connexions HTTP limité. Le courtier se ferme après inactivité ; les tâches planifiées utilisent des requêtes directes plutôt qu'un courtier shell persistant.

Fish utilise-t-il le courtier ?

Oui. Le wrapper Fish démarre et réutilise le même courtier par session que bash et zsh, actualise son bail immédiatement avant une requête ash et maintient la configuration du courtier silencieuse.

Que se passe-t-il si une requête est lente, indisponible ou si je change d'avis ?

Appuyez sur Ctrl-C pour annuler une requête en cours. Le délai d'expiration par défaut de la demande AI est de trois minutes ; définissez AI_TIMEOUT, par exemple AI_TIMEOUT=90s, pour le changer. ash réessaye les échecs d'IA réessayables jusqu'à trois fois par défaut avec un court délai d'attente limité ; ajustez ce comportement avec ASH_RETRY_MAX_ATTEMPTS, ASH_RETRY_BASE_DELAY et ASH_RETRY_MAX_DELAY.

Sécurité et contrôle

Comment verrouiller ash pour être plus sûr, et quelles sont les implications ?

Gardez la liste autorisée des exécutables étroite, privilégiez les outils en lecture seule et n'ajoutez pas de commandes privilégiées ou destructrices. Définissez ASH_STRICT=1 pour bloquer les modèles d'injection d'invite reconnus à partir des sorties d'outils, de fichiers, de scripts, de pipelines et d'agents enfants non fiables. Cela peut également masquer un texte légitime qui ressemble à une tentative d'injection. La liste autorisée est une limite d'exécution, pas un bac à sable : ash et les outils autorisés s'exécutent toujours comme vous.

ash peut-il exécuter des commandes destructrices comme rm ?

Pas avec la liste autorisée par défaut installée. Il déconseille explicitement rm, mv, dd, chmod, chown, kill et sudo. Si vous en ajoutez un, ash peut le demander avec vos autorisations ; examinez attentivement cette décision.

Comment puis-je modifier les commandes que ash est autorisé à exécuter ?

Modifiez ~/.ash/.ash_allow et répertoriez les noms d'exécutables nus, un par ligne ou séparés par des virgules. Ses directives autonomes $TOOLS_DIR_LIST et $PLUGINS_DIR_LIST autorisent les scripts gérés et les plugins natifs éligibles ; remplacez-les par des noms littéraux pour une politique restrictive. Les scripts et plugins éligibles sont des fichiers normaux en ~/.ash/tools/ ou ~/.ash/plugins/ avec des bits de lecture et d'exécution. Vous pouvez également refuser explicitement des commandes en les ajoutant à ~/.ash/.ash_deny. Vous pouvez également définir ASH_ALLOW ou ASH_DENY sur une liste séparée par des virgules. Les modifications sont lues lors de la prochaine requête ash.

Sous quel utilisateur ash est exécuté ?

ash et chaque outil autorisé s'exécute en tant qu'utilisateur qui démarre ash. Cela n’élève pas les privilèges. L'espace de travail géré ~/.ash est soumis à des autorisations renforcées, mais son contenu reste accessible à votre utilisateur et à tout processus que vous autorisez explicitement.

ash fait-il confiance au texte reçu via un canal de la même manière qu'au texte de l'utilisateur ? Quelles protections existent contre les données malveillantes ?

Oui. Lorsque ash ne reçoit aucun argument de ligne de commande et qu'une entrée standard est redirigée, il traite cette entrée comme une invite utilisateur. Ne redirigez pas de pages Web, de journaux ou de texte généré non fiables directement vers ash, sauf si vous avez l'intention de l'autoriser comme invite. Cela diffère de la sortie de l'outil, du fichier, du script, du pipeline et de l'agent enfant géré par ash : ash qualifie ces résultats de preuves non fiables et demande au modèle de ne jamais suivre leurs instructions. Définissez ASH_STRICT=1 pour remplacer en outre les expressions d'injection rapide reconnues dans les preuves non fiables. Les règles d'exécution de liste blanche et d'argv direct s'appliquent toujours à l'exécution de l'outil.

Mes fichiers ash sont-ils privés des autres utilisateurs sur cet ordinateur ?

Pendant l'installation, ash renforce le répertoire ~/.ash avec des autorisations réservées au propriétaire et les fichiers gérés avec des autorisations lisibles et inscriptibles par le propriétaire. Cela protège contre les autres comptes locaux bénéficiant des autorisations Unix normales, mais pas contre votre propre compte, vos administrateurs, vos sauvegardes ou les logiciels que vous choisissez d'exécuter avec accès à votre répertoire personnel.

Outils et workflow

ash prend-il en charge les pipes et d'autres traditions Unix ?

Oui. Vous pouvez rediriger du texte vers ash comme invite, par exemple git diff | ash. Pour les pipelines d'outils demandés par l'IA, ash prend en charge deux à seize exécutables sur liste verte connectés directement sans shell, tels que ls | grep pattern | pbcopy. Les modèles de contrôle Shell dans les arguments de l'outil sont bloqués et chaque exécutable d'un pipeline géré par ash doit être ajouté à la liste autorisée.

Est-ce que ash réinterprétera les commandes dans mes scripts shell, mes commandes SSH ou mes tâches cron ?

Non. Les wrappers d'intégration Bash et zsh reviennent immédiatement dans des shells non interactifs, de sorte que les scripts, les tâches CI, les one-liners SSH et les commandes cron conservent un comportement normal de commande introuvable. Utilisez une invocation explicite telle que ash "summarize this log" ou some-command | ash lorsque l'automatisation doit appeler ash.

Comment empêcher ash d'interpréter mes commandes pendant quelques minutes ?

Exécuter ash snooze pendant les cinq minutes par défaut ou spécifier une durée telle que ash snooze 30s ou ash snooze 1h. Exécutez ash snooze off pour reprendre immédiatement. Snooze interrompt le routage automatique des commandes introuvables et du wrapper ; Les commandes explicites ash ... fonctionnent toujours.

Comment puis-je déboguer ash et voir plus d'informations sur ce qu'il fait ?

Définissez ASH_VERBOSE=1 avant d'exécuter ash pour activer une sortie de débogage structurée et un tableau de bord d'exécution de terminal. Définissez ASH_LOG_FILE pour écrire le JSON de débogage dans un fichier ; ASH_LOG_MAX_BYTES contrôle la rotation et est par défaut de 1 Mio lorsqu'un fichier journal est configuré.

Quelles limites s'appliquent lorsque ash exécute des outils ?

Par défaut, chaque appel d'outil a un délai d'attente de 15 secondes et capture jusqu'à 8 192 octets de sortie. Une requête AI peut effectuer jusqu'à 16 itérations de boucle d'outil, et un pipeline géré par ash comporte de deux à seize étapes. Ajustez le délai d'expiration de l'outil et la limite de sortie avec ASH_TOOL_TIMEOUT et ASH_TOOL_OUTPUT_MAX ; gardez la sortie ciblée avec des commandes telles que head, tail ou grep.

Où se trouve l'invite système par défaut ?

Le fichier d'invite canonique est ~/.ash/.ash_system, installé à partir du fichier par défaut fourni lorsque vous exécutez ash install. ash lit ce fichier en premier. S'il est absent, ash revient à .ash_system dans le répertoire de travail actuel puis à ~/.ash_system. Les valeurs $VARIABLE ordinaires sont développées à partir de l'environnement, mais $TOOLS_DIR_LIST, $PLUGINS_DIR_LIST et $IF_PYTHON_AVAILABLE sont des substitutions Ash internes réservées et jamais dérivées de l'environnement.

Où puis-je mettre mes propres scripts et plugins natifs pour ash appeler comme outils ?

Mettez les scripts Python dans ~/.ash/tools/ et compilez les plugins binaires natifs dans ~/.ash/plugins/. Assurez-vous qu'ils sont exécutables et ajoutez le nom de l'exécutable simple à ~/.ash/.ash_allow (ou comptez sur $TOOLS_DIR_LIST / $PLUGINS_DIR_LIST). ash n'appelle pas de shell pour les commandes et plugins Unix autorisés.

Quelles sont les meilleures pratiques pour un outil ou un plugin afin que l'IA comprenne son objectif et son utilisation ?

Suivez le modèle standard outil/plug-in : exposez des options prévisibles avec des arguments CLI ; et implémentez une option --ai-docs qui explique les capacités, chaque argument et défaut, le schéma de sortie, les états de défaillance et le moment où l'IA doit utiliser l'outil. Émettez du JSON structuré et compact avec un champ status et des détails d'erreur exploitables au lieu d'une prose mélangée à des données. Limitez la sortie, validez les entrées, définissez les délais d'attente du réseau, gérez les pannes attendues et sécurisez les appels répétés de l'outil. Ajoutez son nom de fichier nu à ~/.ash/.ash_allow ; ash ne peut l'exécuter que lorsqu'il est sur la liste autorisée et non répertorié dans ~/.ash/.ash_deny.

Quels sont les scripts d'outils et les plugins natifs fournis ?

Les scripts Python d'amorçage installés sont headlines.py, wikipedia.py et yfinance.py dans ~/.ash/tools/. Les plugins natifs fournis sont what_time_is_it (Go), flip_a_coin (Rust) et calculator (TypeScript) dans ~/.ash/plugins/.

ash peut-il appeler des sous-agents ?

Oui. Un agent parent peut utiliser run_sub_agent pour une tâche ciblée et indépendante. Un enfant hérite du répertoire de travail, de la configuration, des outils et des autorisations du système d'exploitation, renvoie un résultat limité et ne peut pas créer un autre enfant. Le maximum par défaut est de six sous-agents par exécution parent et peut être modifié avec ASH_MAX_AGENTS.

ash peut-il générer des fichiers mémoire pour suivre des tâches complexes et ce qu'il a appris au cours de la session ?

Oui. Il peut écrire des fichiers d'espace de travail persistants sous ~/.ash, qui sont suivis dans ~/.ash/inventory.md, et des fichiers de travail à l'échelle de la session sous ~/.ash/scratch/<session-id>/. Utilisez des fichiers d'espace de travail persistants pour les informations que vous avez l'intention de conserver ; utilisez des fichiers de travail pour les plans temporaires, les notes et les artefacts d'assistance.

ash peut-il planifier le travail pour plus tard ?

Oui, grâce à ses outils d'IA. Sur macOS, la planification ponctuelle utilise un LaunchAgent launchd par utilisateur et nécessite launchctl. Sous Linux, les planifications récurrentes sont prises en charge via votre utilisateur crontab ; ash gère uniquement ses propres entrées marquées. Le planificateur unique launchd n'est pas disponible sous Linux, utilisez donc une entrée cron ou un autre planificateur Linux pour une tâche Linux unique. Les exécutions planifiées bénéficient d'un environnement limité et utilisent HTTPS direct plutôt qu'un courtier shell interactif. Assurez-vous donc que la configuration IA requise est disponible pour la tâche planifiée. Ils ne peuvent pas utiliser les outils MCP distants ; Ash fonctionne sans eux et n'avertit pas lors des sessions non interactives. Ne planifiez pas d'invites nécessitant MCP.

Sessions et stockage

Où se trouvent l'historique ou les fichiers journaux pour ash ?

L'historique des conversations est stocké au format JSON dans ~/.ash/history/<SESSION_ID>.json ; les exécutions planifiées utilisent task_<SESSION_ID>.json. Lorsque la journalisation de débogage planifiée est activée, son emplacement de journal par défaut est ~/.ash/logs/task_<SESSION_ID>.log. Vous pouvez choisir un autre chemin de journal de débogage avec ASH_LOG_FILE.

Combien de temps les fichiers d'historique sont-ils conservés ?

ash supprime les fichiers JSON d'historique de plus de 14 jours lors du nettoyage normal de l'application, avec un budget de nettoyage de 300 ms afin que la sortie ne soit pas retardée. La fenêtre des messages récents est séparée : elle conserve jusqu'à 40 messages par conversation par défaut et peut être modifiée avec ASH_HISTORY_MAX.

Comment effacer une conversation ou recommencer ?

L'historique est séparé par l'ID de session et le point de terminaison/clé de modèle d'IA. Démarrez une nouvelle session de terminal pour un nouvel ID de session ou supprimez le fichier JSON correspondant sous ~/.ash/history/ lorsque vous souhaitez intentionnellement supprimer cet historique de conversation locale. La suppression d'un fichier historique ne révoque pas une clé de fournisseur ni ne supprime les données côté fournisseur ; gérez-les séparément avec le fournisseur.

Qu'est-ce que le SESSION_ID et où est-il généré ?

Il s'agit de l'identifiant par session utilisé pour séparer l'historique, l'espace de travail, les sockets de courtier et les noms de journaux planifiés. L'environnement shell géré génère une valeur alphanumérique aléatoire de 16 caractères à partir de /dev/urandom lorsque le shell démarre ; ash en crée également un lorsqu'une invocation interactive n'a aucune valeur.

Puis-je remplacer l'implémentation du générateur SESSION_ID ?

Vous pouvez fournir votre propre SESSION_ID avant de démarrer ash ou personnaliser votre fichier d'environnement géré local, mais ash le valide. Les identifiants valides comportent au maximum 128 caractères et utilisent des lettres, des chiffres, des traits de soulignement, des traits d'union, avec un suffixe de point facultatif pour la session enfant. N'utilisez pas de valeurs non fiables ou partagées : les collisions combinent l'historique de session et l'état d'exécution.

Support et communauté

Comment signaler un bug ?

Ouvrir un problème sur github.com/Jonconradt/ash/issues avec la version ash, votre système d'exploitation et votre shell, la configuration pertinente au problème avec les secrets étapes supprimées, reproductibles et le résultat observé. Pour une faille de sécurité, n'ouvrez pas de problème public ; signalez-le en privé par e-mail ou par avis de sécurité GitHub.

Y a-t-il un forum de discussion dans le projet ash ?

Oui. Utilisez les Discussions GitHub pour les questions et les idées, et les Problèmes GitHub pour les bugs reproductibles et le suivi du travail.
