Avant de commencer

  1. Système et shell compatibles : macOS ou Linux sur amd64/x86_64 ou arm64/aarch64, ou FreeBSD sur amd64. Utilisez Bash, zsh ou Fish. Les paquets Arch sont uniquement x86_64. Aucun installateur Windows/PowerShell natif n’existe.
  2. Accès aux téléchargements : connexion Internet fonctionnelle et accès HTTPS fiable à GitHub, au dépôt choisi et au fournisseur du modèle. L’inférence locale nécessite aussi un téléchargement initial du modèle.
  3. Permissions : dossier personnel accessible en écriture pour les fichiers utilisateur. Les paquets système Linux et .pkg macOS nécessitent des droits administrateur ; exécutez Homebrew et ash install avec votre utilisateur habituel.
  4. Un modèle : serveur d’inférence local avec modèle téléchargé ou compte cloud/clé API. Choisissez un modèle prenant en charge les appels d’outils, pas uniquement les images/l’audio. Les besoins locaux en RAM, disque et GPU dépendent du modèle.

Les paquets ash précompilés ne nécessitent ni Go, Rust, Node.js, ni outils de compilation Xcode. Le gestionnaire de paquets peut avoir ses propres prérequis ; suivez d’abord sa procédure officielle.

Facultatif : outils Python fournis

L’usage de base ne nécessite pas Python. Les outils Python fournis nécessitent Python 3 avec venv et ensurepip, et l’accès au téléchargement de leurs dépendances. Sur Debian/Ubuntu, installez python3 et python3-venv ; Python Homebrew comprend venv. Sur FreeBSD, utilisez le paquet pip correspondant à votre version Python. Relancez ensuite ash install. Un environnement isolé est créé dans $XDG_DATA_HOME/ash/venv (par défaut ~/.local/share/ash/venv) ; un échec désactive ces outils, pas ash de base.

macOS

Recommandé : Homebrew

Prérequis : Homebrew, un environnement macOS pris en charge et une commande brew fonctionnelle. Le tap sélectionne automatiquement l’archive Intel ou Apple Silicon. Installez Release sans sudo :

brew install Jonconradt/ash/ash
ash version

Homebrew gère les binaires, plugins natifs, pages de manuel et notices de licence dans son préfixe (généralement /opt/homebrew sur Apple Silicon ou /usr/local sur Intel). Il vérifie l’archive avec la somme SHA-256 de la formule. Il ne configure ni fournisseur ni fichier de démarrage du shell : poursuivez avec l’initialisation utilisateur. Mettez à jour avec brew upgrade ash, supprimez Release avec brew uninstall ash ; voir les formules des canaux pour Beta/Nightly.

Alternative : .pkg natif

Téléchargez darwin-arm64.pkg pour Apple Silicon ou darwin-amd64.pkg pour Intel depuis une version publiée. Vérifiez son manifeste signé de sommes de contrôle avant d’ouvrir l’installateur. Des droits administrateur sont requis.

Le paquet macOS n’est ni signé ni notarié. Le manifeste fournit une vérification distincte de l’éditeur/des sommes de contrôle, pas une notarisation Apple. Ne désactivez pas Gatekeeper et ne contournez pas d’avertissement pour installer ash ; préférez Homebrew si votre politique de sécurité l’exige.

Le paquet écrit ash et ash-broker dans /usr/local/bin, les plugins dans /usr/local/lib/ash/plugins, les manuels dans /usr/local/share/man et les notices dans /usr/local/share/licenses/ash. Le reçu est dev.ash.cli. Il n’initialise pas l’utilisateur et n’abonne pas aux mises à jour : initialisez après installation, remplacez-le par un .pkg plus récent vérifié pour actualiser, et suivez la suppression manuelle pour désinstaller. Ne l’installez pas par-dessus une copie gérée par Homebrew.

Linux

Utilisez si possible le gestionnaire de votre distribution. Ces paquets gèrent /usr/bin/ash, /usr/bin/ash-broker, /usr/lib/ash/plugins, les manuels dans /usr/share/man et les notices de licence. Les réglages du fournisseur et hooks du shell relèvent de l’initialisation utilisateur.

Debian et Ubuntu : APT

Prérequis : amd64 ou arm64, droits administrateur, APT, curl, gpg et certificats CA. Installez les outils de téléchargement/clé manquants via votre distribution avant d’ajouter le dépôt. Release s’appelle stable :

sudo apt update
sudo apt install ca-certificates curl gnupg
sudo install -d -m 0755 /etc/apt/keyrings
curl -fsSL https://www.versionx.ai/apt/gpg.key -o versionx-apt.asc
gpg --show-keys --with-fingerprint versionx-apt.asc
sudo gpg --dearmor --batch --yes -o /etc/apt/keyrings/versionx-keyring.gpg versionx-apt.asc
sudo chmod 0644 /etc/apt/keyrings/versionx-keyring.gpg
echo "deb [signed-by=/etc/apt/keyrings/versionx-keyring.gpg] https://www.versionx.ai/apt stable main" |
  sudo tee /etc/apt/sources.list.d/versionx.list
sudo apt update
sudo apt install ash
rm versionx-apt.asc

Avant tout import de clé, vérifiez son empreinte auprès d’une source fiable de l’éditeur. L’empreinte VersionX est 32C6 C11D 2F86 BFE4 6EB7 7FFC 5257 FEA6 1368 919F. APT vérifie les métadonnées signées du dépôt et les condensats des paquets qu’elles contiennent ; signed-by limite la portée de la clé. Mise à jour : sudo apt update && sudo apt upgrade ash ; suppression : sudo apt remove ash.

Fedora et systèmes compatibles RHEL : DNF

Prérequis : x86_64 ou aarch64, droits administrateur, DNF/RPM, curl, gpg et certificats CA. Installez les outils manquants via votre distribution. Inspectez la clé et comparez l’empreinte ci-dessus avant l’import :

curl -fsSL https://www.versionx.ai/rpm/gpg.key -o versionx-rpm.asc
gpg --show-keys --with-fingerprint versionx-rpm.asc
sudo rpm --import versionx-rpm.asc
sudo tee /etc/yum.repos.d/versionx.repo >/dev/null <<'EOF'
[versionx]
name=VersionX ash repository
baseurl=https://www.versionx.ai/rpm/
enabled=1
gpgcheck=0
repo_gpgcheck=1
gpgkey=https://www.versionx.ai/rpm/gpg.key
EOF
sudo dnf install ash
rm versionx-rpm.asc

Les RPM ne sont pas signés individuellement. repo_gpgcheck=1 vérifie les métadonnées couvrant leurs sommes de contrôle ; gpgcheck=0 reflète l’absence de signatures par paquet, pas l’arrêt de la vérification du dépôt. Si votre politique exige des charges RPM signées, ce dépôt ne la satisfait pas. Mise à jour : sudo dnf upgrade ash ; suppression : sudo dnf remove ash.

Arch Linux : Pacman

Prérequis : x86_64, droits administrateur, Pacman avec trousseau initialisé, curl et gpg. Vérifiez que l’empreinte affichée correspond à celle ci-dessus avant de lui faire confiance. Ajoutez le dépôt une seule fois, pas à chaque mise à jour :

curl -fsSL https://www.versionx.ai/pacman/gpg.key -o versionx-pacman.asc
gpg --show-keys --with-fingerprint versionx-pacman.asc
sudo pacman-key --add versionx-pacman.asc
sudo pacman-key --lsign-key 32C6C11D2F86BFE46EB77FFC5257FEA61368919F
sudo tee -a /etc/pacman.conf >/dev/null <<'EOF'
[versionx]
Server = https://www.versionx.ai/pacman/$arch
SigLevel = Required DatabaseRequired
EOF
sudo pacman -Syu ash
rm versionx-pacman.asc

Pacman vérifie les signatures des paquets et de la base. Synchronisez Arch avec sudo pacman -Syu, sans mise à jour partielle ; supprimez ash avec sudo pacman -R ash.

Autres installations Linux

Utilisez-vous déjà Homebrew sur Linux ? Les mêmes instructions du tap prennent en charge amd64 et arm64 ; Brew gère ces fichiers, pas APT/DNF. Sinon utilisez une installation par script/archive vérifiée ou un téléchargement .deb/.rpm adapté. Installez un .deb vérifié avec sudo apt install ./PACKAGE.deb, ou un .rpm avec sudo dnf install ./PACKAGE.rpm (remplacez les noms). Le paquet direct reste géré, mais n’ajoute ni dépôt ni abonnement automatique aux versions futures. La charge RPM actuelle n’est pas signée ; suivez la politique de votre distribution plutôt que de désactiver les vérifications.

FreeBSD

Prérequis : amd64, Bash (même si votre shell interactif est zsh ou Fish), outils de téléchargement/vérification et dossier d’installation accessible en écriture. Installez Bash avec le gestionnaire natif FreeBSD :

sudo pkg install bash

Le pkg de FreeBSD gère les prérequis, pas ash : il n’existe actuellement ni dépôt ash .pkg ni archive arm64. Utilisez le script vérifié, ou vérifiez une archive FreeBSD amd64, extrayez-la dans un dossier temporaire et installez le binaire ash versionné sous ~/.local/bin/ash, à côté de ash-broker. Copiez les plugins natifs dans $XDG_DATA_HOME/ash/plugins (par défaut ~/.local/share/ash/plugins), puis initialisez. Vous gérez ces fichiers ; pkg delete ne les supprime pas. Utilisez les auto-mises à jour Release à l’emplacement par défaut ou remplacez manuellement les fichiers vérifiés.

Initialiser et vérifier

Après les binaires, lancez la configuration interactivement avec votre utilisateur habituel. La configuration des seuls fichiers laisse les fichiers de démarrage inchangés :

ash install

Pour activer aussi l’intégration des commandes introuvables, choisissez exactement une commande correspondant à votre shell :

Bash

ash install --shell bash --shell-integration

zsh

ash install --shell zsh --shell-integration

Fish

ash install --shell fish --shell-integration

Bash utilise ~/.bashrc, zsh ~/.zshrc, Fish $XDG_CONFIG_HOME/fish/config.fish (par défaut ~/.config/fish/config.fish). Ouvrez ensuite un nouveau shell ; les anciens conservent leur broker actif. L’intégration ajoute ~/.local/bin en tête du PATH : supprimez toute ancienne copie locale avant d’attendre la sélection d’un paquet système.

Si les réglages manquent, la configuration détecte les clés existantes ou un serveur local actif ; sinon elle propose un menu de fournisseurs et demande les identifiants. Choisissez un modèle disponible avec appels d’outils. Les réglages valides sont conservés : relancer n’est pas une commande de changement de fournisseur.

Les réglages sont dans $XDG_CONFIG_HOME/ash/.ash_env (par défaut ~/.config/ash/.ash_env, permissions privées). L’intégration gérée les charge. Sans intégration, Bash/zsh peuvent sourcer ce fichier dans leur configuration habituelle ; Fish doit définir les variables ASH_AI_* avec sa syntaxe, sans sourcer le fichier Bash. Protégez les fichiers avec des jetons et ne les commitez jamais.

Pour une installation locale sans intégration, ajoutez son dossier réel au PATH. Bash/zsh : export PATH="$HOME/.local/bin:$PATH". Fish : fish_add_path "$HOME/.local/bin". Rendez cela permanent dans la configuration de démarrage ; substituez votre dossier personnalisé au besoin.

command -v ash
command -v ash-broker
ash version
ash "Say hello in one sentence"

Les premières commandes doivent trouver l’installation choisie. La demande nécessite un serveur actif ou des identifiants cloud valides ; installer ash n’installe pas de modèle.

Ollama local : aucun compte cloud requis

Installez Ollama selon ses instructions officielles pour votre système. Démarrez l’application/service, ou lancez ollama serve dans un autre terminal si aucun serveur ne tourne. Le support FreeBSD d’ash n’implique pas un installateur Ollama natif : utilisez au besoin un serveur accessible sur un autre hôte compatible.

Téléchargez un modèle avec appels d’outils adapté à votre matériel ; llama3.1:8b est un exemple, pas un minimum. Consultez le catalogue actuel des outils pour d’autres modèles :

ollama pull llama3.1:8b
ollama list
curl -fsS http://localhost:11434/api/tags
ash install

Sans clés cloud déjà définies, la configuration peut détecter le serveur local et proposer le modèle téléchargé. Si un autre fournisseur est déjà configuré, changez manuellement le point d’accès/modèle. Exemple Bash/zsh :

export ASH_AI_ENDPOINT="http://localhost:11434"
export ASH_AI_MODEL="llama3.1:8b"
unset ASH_AI_AUTH_TOKEN
ash "Say hello in one sentence"

Équivalent Fish :

set -gx ASH_AI_ENDPOINT http://localhost:11434
set -gx ASH_AI_MODEL llama3.1:8b
set -e ASH_AI_AUTH_TOKEN
ash "Say hello in one sentence"

Ces changements ne concernent que le shell actuel. Enregistrez-les dans votre fichier d’environnement ash protégé ou la configuration du shell, en remplaçant les anciennes substitutions. Ollama local n’a pas besoin de jeton. Gardez le serveur sur loopback sauf accès volontairement sécurisé ; un serveur distant reçoit demandes et sorties d’outils.

Facultatif : définissez OLLAMA_KEEP_ALIVE=30m dans l’environnement du serveur Ollama, puis redémarrez-le pour garder les modèles chargés. -1 les garde indéfiniment mais consomme de la mémoire entre requêtes. Le définir seulement dans le terminal client ash ne reconfigure pas un serveur actif.

L’inférence locale n’a pas de facture API mais utilise votre matériel/stockage/électricité. Ollama cloud est un service distinct avec authentification et limites de forfait, pas cette configuration locale.

Offres cloud gratuites

Gratuit ne signifie ni illimité ni privé. Comptes, régions, quotas, modèles admissibles et politiques de données varient et changent. Demandes et sorties d’outils pertinentes quittent votre machine. Vérifiez limites et conditions actuelles ; n’activez la facturation payante que si vous voulez payer.

Créez une clé avec les liens ci-dessous, lancez ash install interactivement et choisissez le fournisseur. La configuration demande le jeton et liste les modèles si possible. Choisissez un modèle texte gratuit avec appels d’outils actuellement disponible ; sa présence dans la liste ne garantit pas sa gratuité pour votre compte.

Installation par script : une alternative, pas le premier choix

Préférez Homebrew, APT, DNF ou Pacman : ils suivent leurs fichiers, vérifient les téléchargements selon leur configuration de confiance et offrent mises à jour/suppression familières. Ils exigent néanmoins de faire confiance aux éditeurs et actions d’installation.

Un script web exécute du code avec les permissions de votre compte. Un site/éditeur compromis ou un script modifié peut lire des secrets, modifier des fichiers ou installer d’autres logiciels. HTTPS protège le transport, pas l’intention du code. Envoyer directement une URL au shell exécute avant examen. La vérification des signatures d’archives n’authentifie pas le script lui-même. Ne l’exécutez jamais avec sudo et ne désactivez pas sa vérification.

Prérequis : système/architecture compatibles, $SHELL identifiant Bash/zsh/Fish, Sigstore cosign, tar, uname, install, utilitaires shell standards, commande SHA-256 (sha256sum, shasum ou sha256) et téléchargeur (curl, wget ou Python). L’exemple utilise curl. FreeBSD nécessite aussi Bash. Le dossier personnel/d’installation doit être accessible en écriture.

Téléchargez un fichier local, inspectez-le dans un éditeur et exécutez-le uniquement si sa source et son comportement sont fiables. L’examen ne garantit pas la sécurité ; ne suivez pas aveuglément ces étapes :

curl -fsSL https://jonconradt.github.io/ash/install.sh -o ash-install.sh
less ash-install.sh

Après examen, exécutez la copie enregistrée avec votre utilisateur habituel :

sh ./ash-install.sh
rm ./ash-install.sh

install.sh télécharge le dernier Release, vérifie son manifeste signé Sigstore et le condensat de l’archive, puis installe ash/ash-broker dans ~/.local/bin. Les plugins natifs vont dans $XDG_DATA_HOME/ash/plugins. Il configure l’utilisateur et demande avant l’intégration shell. Sans terminal interactif, les questions fournisseur/intégration peuvent être ignorées : lancez ensuite ash install interactivement.

Définissez ASH_INSTALL_DIR avant le script pour choisir une autre destination. Ajoutez-la vous-même au PATH. L’auto-mise à jour est limitée à ~/.local/bin ; toute destination personnalisée nécessite un remplacement manuel. Le script n’a pas de sélecteur Beta/Nightly.

Vérifier un paquet ou une archive directe

Prérequis : cosign et utilitaire SHA-256. Téléchargez le paquet/archive, SHA256SUMS et SHA256SUMS.sigstore.json depuis la même version publiée. Travaillez dans un nouveau dossier. Remplacez vX.Y.Z par l’étiquette exacte, suffixe de préversion inclus si nécessaire :

cosign verify-blob SHA256SUMS \
  --bundle SHA256SUMS.sigstore.json \
  --certificate-identity "https://github.com/Jonconradt/ash/.github/workflows/release.yml@refs/tags/vX.Y.Z" \
  --certificate-oidc-issuer "https://token.actions.githubusercontent.com"

Seulement après réussite, calculez le condensat avec shasum -a 256 PACKAGE sur macOS, sha256sum PACKAGE sur Linux ou sha256 -q PACKAGE sur FreeBSD. Remplacez PACKAGE par le nom téléchargé et comparez exactement à son entrée dans le manifeste vérifié. Arrêtez en cas d’entrée absente ou différence. Une somme non signée téléchargée à côté d’un fichier n’équivaut pas à des métadonnées d’éditeur vérifiées.

Mises à jour et trois canaux

  • Release (recommandé) : versions stables publiées comme vX.Y.Z ; nommé stable dans le dépôt.
  • Beta : tests de préversion, étiquette vX.Y.Z-beta.N ; changements et régressions possibles.
  • Nightly : changements récents de la branche par défaut, étiquette vX.Y.Z-nightly.YYYYMMDD.N ; risque maximal de régression. Les builds sont planifiés mais peuvent être omis sans changements ou lors d’un échec de publication.

Une publication actualise la formule Homebrew ou le dépôt Linux signé correspondant. Vous la recevez en exécutant la mise à niveau du gestionnaire propriétaire, ou selon votre politique système. Publication, dépôts et site peuvent être décalés ; vérifiez la disponibilité avant de changer de canal. ash n’installe pas silencieusement des binaires en arrière-plan.

Homebrew : installer ou changer de formule

Pour une nouvelle installation Beta/Nightly, utilisez le nom complet du tableau dans brew install. Pour changer, désinstallez d’abord la formule actuelle : les trois fournissent les mêmes binaires. Exemple Release vers Beta :

brew uninstall ash
brew install Jonconradt/ash/ash-beta
brew update
brew upgrade ash-beta

Utilisez ash-nightly pour Nightly ou ash pour Release dans les commandes d’installation/mise à niveau. Désinstallez la vraie formule de l’ancien canal, pas systématiquement ash. Les réglages utilisateur restent ; ouvrez ensuite un nouveau shell.

Linux : sélectionner un seul canal de dépôt

APT : suivez la configuration APT avec exactement une distribution du tableau. Pour changer, modifiez /etc/apt/sources.list.d/versionx.list, remplaçant stable par beta ou nightly (ou de nouveau stable), puis :

sudo apt update
sudo apt install --allow-downgrades ash

DNF : suivez la configuration DNF avec la baseurl choisie. Pour une installation existante, remplacez baseurl dans /etc/yum.repos.d/versionx.repo en conservant les réglages de signature, puis :

sudo dnf --refresh distro-sync ash

Pacman : suivez la configuration Pacman avec l’URL Server choisie. Conservez le nom [versionx] : chaque canal publie une base versionx.db. Changez Server dans cette section, n’ajoutez pas une base sous un autre nom. Pour changer, rétrogradation comprise :

sudo pacman -Syuu ash

Examinez la transaction : revenir à Release peut rétrograder ash, et le double u de Pacman aussi d’autres paquets. Sauvegardez la configuration avant le changement. Utilisez ensuite les commandes normales APT/DNF/Pacman des sections système ; n’activez pas plusieurs sources de canaux ash.

Mises à jour Release locales à l’utilisateur

ash update

Ceci vérifie et installe une version stable uniquement si l’exécutable actif est dans ~/.local/bin. Les fichiers/plugins fournis sont aussi actualisés, avec choix pour les fichiers personnalisés. ash update --version vX.Y.Z sélectionne une étiquette stable, pas un canal, et n’est pas une commande de rétrogradation. Pas d’option --channel. Les installations par gestionnaire, .pkg macOS et script à destination personnalisée utilisent leur gestionnaire/installateur. FreeBSD Beta/Nightly utilise des archives vérifiées manuelles, pas un abonnement à l’auto-mise à jour. Ouvrez ensuite un nouveau shell.

Désinstaller sans supprimer les fichiers étrangers

1. Désactiver d’abord l’intégration shell

Avant les binaires, exécutez la commande pour chaque shell où l’intégration est active :

Bash

ash install --shell bash --disable-shell-integration

zsh

ash install --shell zsh --disable-shell-integration

Fish

ash install --shell fish --disable-shell-integration

Si ash manque déjà, modifiez le fichier de démarrage indiqué dans l’initialisation et supprimez uniquement le bloc entre # >>> ash install >>> et # <<< ash install <<<. Supprimez les lignes PATH/environnement ash ajoutées manuellement, pas les autres réglages. Fermez ensuite les shells ash pour arrêter leurs brokers.

2. Laisser le gestionnaire propriétaire supprimer ses fichiers

Homebrew (Release)

brew uninstall ash

APT

sudo apt remove ash

DNF

sudo dnf remove ash

Pacman

sudo pacman -R ash

Choisissez uniquement votre méthode ; pour Homebrew Beta/Nightly, utilisez ash-beta/ash-nightly. APT/DNF/Pacman suppriment binaires, plugins et manuels gérés, pas les réglages/historique personnels. Ne supprimez pas manuellement leurs fichiers.

Nettoyage facultatif du dépôt : supprimez la source ash /etc/apt/sources.list.d/versionx.list et sa clé dédiée /etc/apt/keyrings/versionx-keyring.gpg, le dépôt ash /etc/yum.repos.d/versionx.repo, ou la section ash [versionx] dans /etc/pacman.conf. Vérifiez d’abord qu’aucun autre paquet ne les utilise. Ne retirez une clé RPM/Pacman qu’après vérification de son empreinte et absence d’autres utilisateurs ; jamais le trousseau partagé de la distribution.

3a. Suppression manuelle du .pkg macOS

macOS Installer conserve un reçu mais n’a pas de désinstallateur ash. Confirmez une installation .pkg, pas Homebrew, et examinez son contenu exact :

pkgutil --pkg-info dev.ash.cli
pkgutil --files dev.ash.cli

Avec le reçu comme inventaire, supprimez uniquement les fichiers ash : /usr/local/bin/ash, /usr/local/bin/ash-broker, fichiers de /usr/local/lib/ash/plugins, /usr/local/share/man/man1/ash.1, pages ash.1 traduites indiquées et notices dans /usr/local/share/licenses/ash. Des droits administrateur sont nécessaires. Vérifiez la propriété si un autre installateur les a remplacés ; ne supprimez pas sa copie. Supprimez les dossiers vides propres à ash, pas les dossiers partagés /usr/local, bin ou de manuels.

Après les fichiers, retirez éventuellement le reçu :

sudo pkgutil --forget dev.ash.cli

Oublier un reçu ne supprime aucun fichier installé. Gardez-le jusqu’à la fin de la vérification du contenu.

3b. Suppression manuelle d’archives locales / Linux / FreeBSD

Repérez la copie active avec command -v ash et command -v ash-broker. Après désactivation des hooks, supprimez exactement ces deux fichiers pour l’installation script par défaut :

rm "$HOME/.local/bin/ash" "$HOME/.local/bin/ash-broker"

Pour ASH_INSTALL_DIR ou une archive extraite manuellement, supprimez seulement les véritables chemins ash/broker. Retirez plugins/manuels/notices installés selon l’inventaire d’origine ; les plugins du script sont dans les données utilisateur ash. Dans /usr/bin, vérifiez d’abord la propriété avec dpkg -S /usr/bin/ash, rpm -qf /usr/bin/ash ou pacman -Qo /usr/bin/ash. Une copie gérée doit être supprimée par son gestionnaire, même issue d’un téléchargement autonome.

4. Facultatif : effacer réglages, outils et historique locaux

Sauvegardez tout ce que vous souhaitez garder. Cette étape distincte peut effacer réglages/jetons, outils/plugins personnalisés, historique et fichiers de travail. Désinstaller les binaires ne vaut pas consentement à cet effacement.

  • Configuration : $XDG_CONFIG_HOME/ash, par défaut ~/.config/ash.
  • Données, plugins et environnement Python : $XDG_DATA_HOME/ash, par défaut ~/.local/share/ash.
  • Historique et état : $XDG_STATE_HOME/ash, par défaut ~/.local/state/ash.
  • Cache : $XDG_CACHE_HOME/ash, par défaut ~/.cache/ash.
  • Exécution du broker : $XDG_RUNTIME_DIR/ash, ou $XDG_STATE_HOME/ash/runtime sans racine d’exécution disponible.

Inspectez les substitutions XDG absolues réelles avant de supprimer uniquement ces sous-dossiers ash ; jamais une racine XDG ou le dossier personnel. Après fermeture de tous les shells ash, supprimez au besoin les restes d’exécution. Des identifiants MCP OAuth peuvent rester dans le gestionnaire du système : supprimez les entrées ash et révoquez l’accès chez le fournisseur MCP. Révoquez les clés IA inutilisées chez leur fournisseur ; supprimer un fichier ne révoque pas la clé. Ne désinstallez pas Ollama/modèles, Python ou dépendances partagées avec ash.

Dépannage rapide

Commande absente ou mauvaise version
Vérifiez PATH et command -v ash/command -v ash-broker. Une ancienne copie dans ~/.local/bin peut masquer un paquet. Utilisez un seul propriétaire/canal à la fois, puis un nouveau shell.
Menu fournisseur absent
Lancez ash install dans un terminal interactif. Les réglages valides restent ; utilisez la configuration manuelle pour changer. Sans intégration, exportez les réglages dans l’environnement CLI.
Modèle absent ou connexion refusée
Pour Ollama, vérifiez le serveur et la présence du modèle dans ollama list. Pour le cloud, vérifiez point d’accès, admissibilité, HTTPS, jeton et quota ; ne partagez jamais de journaux avec jetons.
Dépôt ou canal indisponible
Vérifiez l’architecture et la version/le dépôt publié. Une publication peut tarder ; ne désactivez pas les signatures pour contourner un dépôt indisponible.
Échec de configuration Python
Installez Python avec venv/ensurepip, autorisez les téléchargements de dépendances et relancez ash install. ash de base reste utilisable sans ces outils.
