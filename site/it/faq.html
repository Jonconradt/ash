Per iniziare

Di cosa ho bisogno prima di poter utilizzare ash?

È necessario l'eseguibile ash, un endpoint AI e un nome di modello. L'esecuzione di ash install li configura automaticamente: utilizza una chiave API del provider cloud già impostata o un server di inferenza locale in esecuzione quando viene trovato, altrimenti mostra un menu del provider numerato e richiede una chiave API, quindi consente di scegliere un modello dall'elenco dei modelli dell'endpoint. Puoi anche impostare manualmente AI_ENDPOINT e AI_MODEL. Un endpoint locale come Ollama può utilizzare http://localhost:11434 e anche un host LAN come http://brain.local:11434 o un IP privato viene trattato come locale (a meno che ASH_STRICT=1); gli endpoint cloud devono utilizzare HTTPS e richiedono anche AI_AUTH_TOKEN. L'integrazione della shell è facoltativa: puoi sempre eseguire ash "your question" direttamente.

Dove si installa ash e come posso verificare che la mia shell possa trovarlo?

Il programma di installazione verificato inserisce ash in ~/.local/bin/ash e ash install aggiunge quella directory al tuo PATH tramite il file ~/.ash/.ash_env gestito. Apri un nuovo terminale, quindi esegui command -v ash per confermare. L'autoaggiornamento installa il suo binario sostitutivo nella stessa posizione ~/.local/bin/ash.

Come posso utilizzare ash senza cambiare la shell?

Passa direttamente un prompt tra virgolette: ash "how do I find large files?". Senza argomenti, ash accetta anche un prompt di input standard non interattivo, come git diff | ash. L'uso diretto è l'opzione meno sorprendente quando stai imparando ash o scrivi uno script.

Perché ash dice che la mia configurazione AI è incompleta?

Verifica che AI_ENDPOINT e AI_MODEL non siano vuoti nell'ambiente in cui viene eseguito ash. Per un nome host cloud, imposta anche AI_AUTH_TOKEN. Esegui printf '%s\n' "$AI_ENDPOINT" "$AI_MODEL" per confermare che i primi due valori sono presenti, ma non stampare un token di autenticazione in una registrazione del terminale o in un registro condiviso.

Installazione e aggiornamento

ash funziona su Windows 11?

Non in modo nativo. ash supporta bash, zsh e Fish su macOS, Linux e FreeBSD; non esiste una destinazione di installazione di PowerShell. Utilizza WSL per l'esperienza Linux supportata.

Come faccio a installare ash nel sottosistema Windows per Linux (WSL)?

Installalo all'interno della distribuzione WSL come Linux: curl -fsSL https://jonconradt.github.io/ash/install.sh | sh. Quindi configura AI_ENDPOINT e AI_MODEL ed esegui ash install per la shell in esecuzione all'interno di WSL.

Come faccio ad aggiornare ash all'ultima versione?

Esegui ash update su macOS, Linux o FreeBSD. Scarica l'ultimo archivio corrispondente stabile, verifica il manifest di rilascio con il bundle Sigstore e il digest SHA-256, quindi si installa in ~/.local/bin/ash. Se la verifica della firma fallisce o l'archivio contiene voci non supportate, è richiesta una conferma interattiva; non approvare una firma non riuscita a meno che non ti fidi in modo indipendente della fonte di rilascio. I payload non supportati vengono ignorati e le esecuzioni non interattive rifiutano queste eccezioni. Utilizzare ash update --version vX.Y.Z per una versione specifica; usa --yes solo quando vuoi sostituire i file gestiti personalizzati.

Ho eseguito ash install. Perché non cambia nulla in questo terminale?

L'installazione aggiorna un file di avvio; non riscrive il processo di shell già in esecuzione. Apri un nuovo terminale o ricarica il file per la tua shell: source ~/.bashrc per Bash, source ~/.zshrc per zsh o source ~/.config/fish/config.fish per Fish a meno che non usi un XDG_CONFIG_HOME personalizzato.

I comandi sconosciuti dicono ancora "non trovato". Come posso risolvere i problemi di integrazione della shell?

Prima esecuzione command -v ash; il wrapper non può invocare un binario che la tua shell non riesce a trovare. Quindi ricarica o riavvia la shell e controlla che il suo file di avvio contenga il blocco gestito >>> ash install >>>. Infine esegui ash snooze off, perché una ripetizione lascia intenzionalmente i comandi sconosciuti come normali errori "non trovati".

Quali file cambia ash install e posso visualizzarne l'anteprima?

Aggiunge o aggiorna un blocco contrassegnato ash nel file di avvio della shell selezionato e gestisce i file in ~/.ash, inclusa la configurazione, wrapper e strumenti in bundle. Esegui ash install --shell bash --dry-run per visualizzare in anteprima la modifica del file di avvio senza scriverla. La riesecuzione dell'installazione è idempotente; usa --overwrite solo quando vuoi aggiornare i file bootstrap gestiti.

ash supporta Fish?

Sì. Esegui ash install --shell fish. ash aggiunge un blocco gestito a $XDG_CONFIG_HOME/fish/config.fish o ~/.config/fish/config.fish quando XDG_CONFIG_HOME non è impostato. Fish utilizza fish_command_not_found, quindi un comando non risolto raggiunge ash con i suoi argomenti originali.

Perché non test e type in minuscolo in Fish?

Fish riserva questi nomi minuscoli come builtin essenziali e non consente a una funzione di sostituirli. Utilizza Test ... o Type ... per esprimere l'intento ash o invoca direttamente ash "...". Restano disponibili altri wrapper di collisione compatibili.

E ksh93?

ksh93 non è supportato per l'integrazione della shell. Il suo comportamento FPATH può caricare solo un file che prende il nome da un comando sconosciuto; non dispone di una richiamata generica di comando non trovato che possa implementare in modo sicuro il routing del prompt ash o il ciclo di vita del broker.

AI e connessioni

ash include l'intelligenza artificiale?

No. ash è un client per un endpoint AI configurato da te. Imposta AI_ENDPOINT e AI_MODEL; ash supporta Ollama locale e altri server locali compatibili con OpenAI (LM Studio, llama.cpp, MLX, LocalAI, vLLM, text- generation-webui, Jan, GPT4All) e rileva gli adattatori del provider cloud supportati dall'endpoint, con una sostituzione AI_PROVIDER opzionale.

Cosa sono i server MCP e come posso aggiungerli uno?

I server MCP (Model Context Protocol) espongono strumenti che un modello AI può chiamare, come ricerca, analisi o azioni specifiche del servizio. Per aggiungere un server MCP HTTP streaming remoto, inserisci il suo URL sulla propria riga in ~/.ash/.ash_allow, quindi esegui nuovamente ash. Ad esempio: https://mcpplaygroundonline.com/mcp-complex-server. Ash si connette tramite il suo broker e offre gli strumenti del server al modello. Utilizza solo server di cui ti fidi: i loro strumenti potrebbero eseguire azioni per tuo conto. È richiesto HTTPS, ad eccezione dei server di sviluppo localhost. I file ~/.ash/mcp.json esistenti non vengono più letti; sposta i loro URL in .ash_allow. Se l'inizializzazione MCP fallisce, ash continua senza strumenti MCP remoti: avvisa nelle sessioni interattive e rimane silenzioso nelle sessioni non interattive.

I lavori pianificati possono utilizzare i server MCP?

No. I lavori pianificati e altri lavori non interattivi non ereditano il broker di una shell interattiva, quindi gli strumenti MCP remoti non sono disponibili. Ash esegue ancora il prompt senza strumenti MCP ed elimina questo errore di inizializzazione previsto. Un prompt che si basa su MCP potrebbe quindi terminare senza i dati o l'azione richiesti. Non pianificare richieste che richiedono MCP.

MCP funziona quando ASH_STRICT=1?

Sì. Una riga URL HTTP(S) registra esplicitamente un server MCP e non viene trattata come un eseguibile della shell. La modalità rigorosa non disabilita i server MCP configurati. Applica ancora le protezioni dell'output non attendibile di Ash al contenuto dello strumento restituito.

Come funziona MCP OAuth e dove sono archiviate le credenziali?

Per un server protetto da OAuth, Ash apre la pagina di autorizzazione nel browser desktop quando è disponibile una GUI; se non riesce ad aprire un browser, stampa un URL per autorizzare manualmente in un browser sullo stesso host. Utilizza ash mcp add <url> --no-browser per utilizzare sempre il flusso terminale. Per le connessioni OAuth dirette, il rilevamento consente indirizzi IP non pubblici solo per l'esatta autorità MCP registrata; gli altri host OAuth rimangono soggetti al blocco degli indirizzi non pubblici. Un proxy di uscita configurato è responsabile del filtraggio dei propri indirizzi di destinazione. Il broker gestisce la richiamata, lo scambio di token, l'aggiornamento e la sessione MCP persistente. Le credenziali vengono archiviate nel gestore credenziali del sistema operativo quando disponibili. Se non è disponibile, configura il fallback del file crittografato utilizzando un ASH_MCP_CREDENTIAL_KEY casuale da 32 byte; Ash non memorizza mai la chiave stessa.

Dove posso trovare AUTH_KEY per i provider di intelligenza artificiale cloud più popolari?

ash chiama questo valore AI_AUTH_TOKEN; non crea né distribuisce chiavi del provider. Crea una chiave nell'account del tuo provider, ad esempio OpenAI, Anthropic, Google AI Studio, Azure OpenAI, Mistral, Cohere, Groq, xAI, DeepSeek, Together AI, OpenRouter, HuggingFace o Ollama, quindi esportalo come variabile di ambiente del provider (o direttamente AI_AUTH_TOKEN). ash install rileva automaticamente la maggior parte di queste variabili di ambiente specifiche del provider. Gli endpoint cloud devono utilizzare HTTPS e richiedere un token; gli indirizzi LAN/privati ​​e i nomi host .local non vengono trattati come endpoint cloud a meno che non sia impostato ASH_STRICT=1.

ash apre una nuova connessione ogni volta?

Non per il normale utilizzo interattivo della shell Unix. Bash, zsh e Fish avviano un broker per sessione di shell, comunicano con esso tramite un socket Unix privato e riutilizzano il suo pool di connessioni HTTP limitato. Il broker esce dopo l'inattività; i lavori pianificati utilizzano richieste dirette anziché un broker di shell persistente.

Fish utilizza il broker?

Sì. Il wrapper Fish avvia e riutilizza lo stesso broker per sessione di bash e zsh, aggiorna il suo lease immediatamente prima di una richiesta ash e mantiene silenziosa la configurazione del broker.

Cosa succede se una richiesta è lenta, non disponibile o cambio idea?

Premi Ctrl-C per annullare una richiesta in corso. Il timeout predefinito della richiesta AI è di tre minuti; impostare AI_TIMEOUT, ad esempio AI_TIMEOUT=90s, per cambiarlo. ash riprova gli errori AI ripetibili fino a tre volte per impostazione predefinita con un breve backoff limitato; ottimizza questo comportamento con ASH_RETRY_MAX_ATTEMPTS, ASH_RETRY_BASE_DELAY e ASH_RETRY_MAX_DELAY.

Sicurezza e controllo

Come posso bloccare ash per essere più sicuro e quali sono le implicazioni?

Mantieni la lista consentita degli eseguibili ristretta, favorisci strumenti di sola lettura e non aggiungere comandi privilegiati o distruttivi. Imposta ASH_STRICT=1 per bloccare i modelli di prompt-injection riconosciuti da strumenti, file, script, pipeline e output dell'agente figlio non attendibili. Ciò può anche nascondere testo legittimo che assomiglia a un tentativo di injection. La lista consentita è un limite di esecuzione, non una sandbox: ash e gli strumenti consentiti continuano a essere eseguiti come te.

ash può eseguire comandi distruttivi come rm?

Non con la lista consentita predefinita installata. Sconsiglia esplicitamente rm, mv, dd, chmod, chown, kill e sudo. Se ne aggiungi uno, ash può richiederlo con le tue autorizzazioni; rivedi attentamente tale decisione.

Come posso modificare i comandi che ash può eseguire?

Modifica ~/.ash/.ash_allow ed elenca i nomi degli eseguibili semplici, uno per riga o separati da virgole. Le sue direttive autonome $TOOLS_DIR_LIST e $PLUGINS_DIR_LIST consentono script gestiti idonei e plugin nativi; sostituirli con nomi letterali per una politica restrittiva. Gli script e i plugin idonei sono file regolari in ~/.ash/tools/ o ~/.ash/plugins/ con bit di lettura ed esecuzione. Puoi anche negare esplicitamente i comandi aggiungendoli a ~/.ash/.ash_deny. In alternativa, imposta ASH_ALLOW o ASH_DENY su un elenco separato da virgole. Le modifiche vengono lette alla successiva richiesta ash.

Con quale utente è in esecuzione ash?

ash e ogni strumento consentito viene eseguito come utente che avvia ash. Non eleva i privilegi. L'area di lavoro gestita ~/.ash ha autorizzazioni rafforzate, ma i suoi contenuti rimangono accessibili all'utente e a qualsiasi processo esplicitamente consentito.

ash considera attendibile il testo ricevuto tramite pipe come il testo dell'utente? Quali protezioni esistono per i dati dannosi?

Sì. Quando ash non riceve argomenti della riga di comando e viene inviato tramite pipe l'input standard, considera tale input come il prompt dell'utente. Non reindirizzare pagine Web, registri o testo generato non attendibili direttamente a ash a meno che non intendi autorizzarlo come prompt. Ciò differisce dall'output di strumenti, file, script, pipeline e agenti secondari gestiti da ash: ash etichetta tali risultati come prove non attendibili e indica al modello di non seguire mai le istruzioni da essi. Imposta ASH_STRICT=1 per sostituire ulteriormente le frasi riconosciute di iniezione rapida in prove non attendibili. Le regole di esecuzione della lista consentita e dell'argv diretto si applicano ancora all'esecuzione dello strumento.

I miei file ash sono privati ​​da altri utenti su questo computer?

Durante l'installazione, ash rafforza la directory ~/.ash con autorizzazioni riservate al proprietario e i file gestiti con autorizzazioni leggibili e scrivibili dal proprietario. Ciò protegge da altri account locali con normali autorizzazioni Unix, ma non dal tuo account, dagli amministratori, dai backup o dal software che scegli di eseguire con accesso alla tua directory home.

Strumenti e flusso di lavoro

ash supporta pipe e altre tradizioni Unix?

Sì. Puoi reindirizzare il testo in ash come prompt, ad esempio git diff | ash. Per le pipeline di strumenti richiesti dall'intelligenza artificiale, ash supporta da due a sedici eseguibili consentiti collegati direttamente senza shell, come ls | grep pattern | pbcopy. I modelli di controllo della shell negli argomenti dello strumento sono bloccati e ogni eseguibile in una pipeline gestita da ash deve essere inserito nella lista consentita.

ash reinterpreterà i comandi all'interno dei miei script di shell, comandi SSH o lavori cron?

No. I wrapper di integrazione Bash e zsh ritornano immediatamente in shell non interattive, quindi script, processi CI, one-liner SSH e comandi cron mantengono il normale comportamento di comando non trovato. Utilizza un'invocazione esplicita come ash "summarize this log" o some-command | ash quando l'automazione deve chiamare ash.

Come posso impedire a ash di interpretare i miei comandi per alcuni minuti?

Esegui ash snooze per i cinque minuti predefiniti o specifica una durata come ash snooze 30s o ash snooze 1h. Esegui ash snooze off per riprendere immediatamente. La funzione Snooze sospende il routing automatico dei comandi non trovati e del wrapper; i comandi espliciti ash ... funzionano ancora.

Come posso eseguire il debug di ash e visualizzare maggiori informazioni su ciò che sta facendo?

Imposta ASH_VERBOSE=1 prima di eseguire ash per abilitare l'output di debug strutturato e un dashboard di esecuzione del terminale. Imposta ASH_LOG_FILE per scrivere il JSON di debug in un file; ASH_LOG_MAX_BYTES controlla la rotazione e per impostazione predefinita è 1 MiB quando viene configurato un file di registro.

Quali limiti si applicano quando ash esegue gli strumenti?

Per impostazione predefinita, ogni chiamata allo strumento ha un timeout di 15 secondi e acquisisce fino a 8192 byte di output. Una richiesta AI può comprendere fino a 16 iterazioni del ciclo di strumenti e una pipeline gestita da ash ha da due a sedici fasi. Regola il timeout dello strumento e il limite di output con ASH_TOOL_TIMEOUT e ASH_TOOL_OUTPUT_MAX; mantieni l'output focalizzato con comandi come head, tail o grep.

Dov'è il prompt di sistema predefinito?

Il file di prompt canonico è ~/.ash/.ash_system, installato dall'impostazione predefinita in bundle quando si esegue ash install. ash legge prima quel file. Se è assente, ash ritorna a .ash_system nella directory di lavoro corrente e poi a ~/.ash_system. I valori ordinari $VARIABLE vengono espansi dall'ambiente, ma $TOOLS_DIR_LIST, $PLUGINS_DIR_LIST e $IF_PYTHON_AVAILABLE sono sostituzioni interne riservate Ash e mai derivate dall'ambiente.

Dove inserisco i miei script e i plugin nativi per ash da chiamare come strumento?

Inserisci gli script Python in ~/.ash/tools/ e compila i plugin binari nativi in ~/.ash/plugins/. Assicurati che siano eseguibili e aggiungi il semplice nome dell'eseguibile a ~/.ash/.ash_allow (o fai affidamento su $TOOLS_DIR_LIST / $PLUGINS_DIR_LIST). ash non invoca una shell per comandi e plugin Unix consentiti.

Quali sono le migliori pratiche per uno strumento o plugin in modo che l'intelligenza artificiale ne comprenda lo scopo e l'utilizzo?

Segui il modello standard di strumento/plugin: esponi opzioni prevedibili con argomenti CLI; e implementare un'opzione --ai-docs che spiega le funzionalità, ogni argomento e impostazione predefinita, lo schema di output, gli stati di errore e quando l'intelligenza artificiale dovrebbe utilizzare lo strumento. Emetti un JSON strutturato compatto con un campo status e dettagli sugli errori utilizzabili invece di prosa mescolata con dati. Mantieni l'output limitato, convalida gli input, imposta i timeout di rete, gestisci gli errori previsti e rendi lo strumento sicuro da chiamare ripetutamente. Aggiungi il suo semplice nome file a ~/.ash/.ash_allow; ash può eseguirlo solo quando è nella lista consentita e non è elencato in ~/.ash/.ash_deny.

Quali sono gli script degli strumenti forniti e i plugin nativi?

Gli script Python bootstrap installati sono headlines.py, wikipedia.py e yfinance.py in ~/.ash/tools/. I plugin nativi forniti sono what_time_is_it (Go), flip_a_coin (Rust) e calculator (TypeScript) in ~/.ash/plugins/.

Può ash chiamare agenti secondari?

Sì. Un agente principale può utilizzare run_sub_agent per un'attività mirata e indipendente. Un figlio eredita la directory di lavoro, la configurazione, gli strumenti e le autorizzazioni del sistema operativo, restituisce un risultato limitato e non può creare un altro figlio. Il massimo predefinito è sei agenti secondari per esecuzione principale e può essere modificato con ASH_MAX_AGENTS.

ash può generare file di memoria per tenere traccia di attività complesse e di ciò che ha appreso nella sessione?

Sì. Può scrivere file di spazio di lavoro persistenti in ~/.ash, che vengono tracciati in ~/.ash/inventory.md e file scratch con ambito sessione in ~/.ash/scratch/<session-id>/. Utilizza file di spazio di lavoro persistenti per le informazioni che intendi conservare; utilizza file temporanei per piani temporanei, note e elementi di supporto.

ash può pianificare il lavoro per dopo?

Sì, attraverso i suoi strumenti di intelligenza artificiale. Su macOS, la pianificazione una tantum utilizza un LaunchAgent launchd per utente e richiede launchctl. Su Linux, le pianificazioni ricorrenti sono supportate tramite l'utente crontab; ash gestisce solo le proprie voci contrassegnate. Lo scheduler una tantum launchd non è disponibile su Linux, quindi utilizza una voce cron o un altro scheduler Linux per un lavoro Linux una tantum. Le esecuzioni pianificate ricevono un ambiente limitato e utilizzano HTTPS diretto anziché un broker di shell interattivo, quindi assicurati che la configurazione AI richiesta sia disponibile per il processo pianificato. Non possono utilizzare strumenti MCP remoti; Ash funziona senza di essi e non avvisa nelle sessioni non interattive. Non pianificare richieste che richiedono MCP.

Sessioni e archiviazione

Dove si trovano la cronologia o i file di registro per ash?

La cronologia delle conversazioni è archiviata come JSON in ~/.ash/history/<SESSION_ID>.json; le corse programmate utilizzano task_<SESSION_ID>.json. Quando la registrazione di debug pianificata è abilitata, il percorso predefinito del registro è ~/.ash/logs/task_<SESSION_ID>.log. Puoi scegliere un altro percorso di registro di debug con ASH_LOG_FILE.

Per quanto tempo vengono conservati i file di cronologia?

ash rimuove i file JSON di cronologia più vecchi di 14 giorni durante la normale pulizia dell'applicazione, con un budget di pulizia di 300 ms in modo che l'uscita non venga ritardata. La finestra dei messaggi recenti è separata: conserva fino a 40 messaggi per conversazione per impostazione predefinita e può essere modificata con ASH_HISTORY_MAX.

Come posso cancellare una conversazione o ricominciare da capo?

La cronologia è separata per ID sessione e chiave endpoint/modello AI. Avvia una nuova sessione terminale per un nuovo ID sessione o rimuovi il file JSON pertinente in ~/.ash/history/ quando desideri eliminare intenzionalmente la cronologia delle conversazioni locali. La rimozione di un file di cronologia non revoca la chiave del provider né elimina i dati lato provider; gestiscili separatamente con il provider.

Cos'è SESSION_ID e dove viene generato?

È l'identificatore per sessione utilizzato per separare cronologia, spazio di lavoro, socket del broker e nomi di log pianificati. L'ambiente della shell gestita genera un valore alfanumerico casuale di 16 caratteri da /dev/urandom all'avvio della shell; ash ne crea uno anche quando un'invocazione interattiva non ha valore.

Posso sostituire l'implementazione del generatore SESSION_ID?

Puoi fornire il tuo SESSION_ID prima di iniziare ash o personalizzare il file dell'ambiente gestito locale, ma ash lo convalida. Gli ID validi contengono al massimo 128 caratteri e utilizzano lettere, cifre, caratteri di sottolineatura, trattini, con un suffisso punto facoltativo per la sessione figlio. Non utilizzare valori non attendibili o condivisi: le collisioni combinano la cronologia della sessione e lo stato di runtime.

Supporto e community

Come faccio a segnalare un bug?

Apri un problema su github.com/Jonconradt/ash/issues con la versione ash o commit, il tuo sistema operativo e la shell, la configurazione relativa al problema con i segreti passaggi rimossi e riproducibili e il risultato osservato. Per una vulnerabilità della sicurezza, non aprire un problema pubblico; segnalalo in privato tramite e-mail o avviso di sicurezza su GitHub.

C'è un forum di discussione nel progetto ash?

Sì. Utilizza le Discussioni GitHub per domande e idee e i Problemi GitHub per bug riproducibili e lavoro monitorato.
