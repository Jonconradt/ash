Bevor Sie beginnen

  1. Unterstütztes System und Shell: macOS oder Linux auf amd64/x86_64 oder arm64/aarch64, oder FreeBSD auf amd64. Verwenden Sie Bash, zsh oder Fish. Arch-Pakete unterstützen nur x86_64. Es gibt keinen nativen Windows-/PowerShell-Installer.
  2. Downloadzugang: funktionierende Internetverbindung und vertrauenswürdiger HTTPS-Zugang zu GitHub, dem gewählten Paket-Repository und Ihrem Modellanbieter. Auch lokale Inferenz benötigt einen anfänglichen Modelldownload.
  3. Berechtigungen: beschreibbares Home-Verzeichnis für benutzerspezifische Dateien. Linux-Systempakete und macOS-.pkg benötigen Administratorrechte; führen Sie Homebrew und ash install als normaler Benutzer aus.
  4. Ein Modell: lokaler Inferenzserver mit heruntergeladenem Modell oder Cloud-Konto/API-Schlüssel. Wählen Sie ein Modell mit Werkzeugaufrufen, kein reines Bild-/Audiomodell. Lokaler RAM-, Speicher- und GPU-Bedarf hängt vom Modell ab.

Vorgefertigte ash-Pakete benötigen weder Go, Rust, Node.js noch Xcode-Buildwerkzeuge. Paketverwaltungen können eigene Voraussetzungen haben; befolgen Sie zuerst deren offizielle Einrichtung.

Optional: mitgelieferte Python-Werkzeuge

Die grundlegende Nutzung benötigt kein Python. Mitgelieferte Python-Werkzeuge benötigen Python 3 mit venv und ensurepip sowie Zugang zum Herunterladen ihrer Abhängigkeiten. Installieren Sie auf Debian/Ubuntu python3 und python3-venv; Homebrew-Python enthält venv-Unterstützung. Verwenden Sie auf FreeBSD das pip-Paket passend zur Python-Version. Führen Sie anschließend ash install erneut aus. Die Einrichtung erstellt eine isolierte Umgebung unter $XDG_DATA_HOME/ash/venv (Standard: ~/.local/share/ash/venv); bei Fehlern werden nur diese Werkzeuge deaktiviert, nicht ash selbst.

macOS

Empfohlen: Homebrew

Voraussetzungen: Homebrew, eine unterstützte macOS-Umgebung und ein funktionierender brew-Befehl. Der Tap wählt automatisch das Intel- oder Apple-Silicon-Archiv. Installieren Sie Release ohne sudo:

brew install Jonconradt/ash/ash
ash version

Homebrew verwaltet Binärdateien, native Plugins, Handbuchseiten und Lizenzhinweise in seinem Präfix (gewöhnlich /opt/homebrew auf Apple Silicon oder /usr/local auf Intel). Es prüft das Archiv anhand der SHA-256-Prüfsumme der Formel. Anbieter und Shell-Startdatei werden nicht konfiguriert: fahren Sie mit der benutzerspezifischen Initialisierung fort. Aktualisieren Sie mit brew upgrade ash, entfernen Sie Release mit brew uninstall ash; für Beta/Nightly siehe Kanalformeln.

Alternative: natives .pkg

Laden Sie darwin-arm64.pkg für Apple Silicon oder darwin-amd64.pkg für Intel aus einer veröffentlichten Version herunter. Prüfen Sie das signierte Prüfsummenmanifest, bevor Sie den Installer öffnen. Administratorrechte sind erforderlich.

Das macOS-Paket ist weder signiert noch notarisiert. Das Versionsmanifest bietet eine separate Herausgeber-/Prüfsummenprüfung, keine Apple-Notarisierung. Deaktivieren Sie weder Gatekeeper noch umgehen Sie Sicherheitswarnungen nur zur Installation; bevorzugen Sie Homebrew, wenn Ihre Sicherheitsrichtlinie dies verlangt.

Das Paket schreibt ash und ash-broker nach /usr/local/bin, Plugins nach /usr/local/lib/ash/plugins, Handbuchseiten nach /usr/local/share/man und Hinweise nach /usr/local/share/licenses/ash. Der Beleg lautet dev.ash.cli. Es initialisiert keine Benutzereinstellungen und abonniert keine Updates: initialisieren Sie anschließend, aktualisieren Sie durch ein neueres verifiziertes .pkg und verwenden Sie zur Deinstallation das manuelle Entfernen. Installieren Sie es nicht über eine von Homebrew verwaltete Kopie.

Linux

Verwenden Sie möglichst die Paketverwaltung Ihrer Distribution. Diese Pakete verwalten /usr/bin/ash, /usr/bin/ash-broker, /usr/lib/ash/plugins, Handbuchseiten unter /usr/share/man und Lizenzhinweise. Anbietereinstellungen und Shell-Hooks bleiben der benutzerspezifischen Initialisierung überlassen.

Debian und Ubuntu: APT

Voraussetzungen: amd64 oder arm64, Administratorrechte, APT, curl, gpg und CA-Zertifikate. Installieren Sie fehlende Download-/Schlüsselwerkzeuge aus Ihrer Distribution, bevor Sie das Repository hinzufügen. Release heißt stable:

sudo apt update
sudo apt install ca-certificates curl gnupg
sudo install -d -m 0755 /etc/apt/keyrings
curl -fsSL https://www.versionx.ai/apt/gpg.key -o versionx-apt.asc
gpg --show-keys --with-fingerprint versionx-apt.asc
sudo gpg --dearmor --batch --yes -o /etc/apt/keyrings/versionx-keyring.gpg versionx-apt.asc
sudo chmod 0644 /etc/apt/keyrings/versionx-keyring.gpg
echo "deb [signed-by=/etc/apt/keyrings/versionx-keyring.gpg] https://www.versionx.ai/apt stable main" |
  sudo tee /etc/apt/sources.list.d/versionx.list
sudo apt update
sudo apt install ash
rm versionx-apt.asc

Prüfen Sie vor jedem Schlüsselimport den Fingerabdruck anhand einer vertrauenswürdigen Herausgeberquelle. Der VersionX-Fingerabdruck ist 32C6 C11D 2F86 BFE4 6EB7 7FFC 5257 FEA6 1368 919F. APT prüft signierte Repository-Metadaten und darin enthaltene Paketprüfsummen; signed-by begrenzt den Schlüsselbereich. Aktualisieren: sudo apt update && sudo apt upgrade ash; entfernen: sudo apt remove ash.

Fedora und RHEL-kompatible Systeme: DNF

Voraussetzungen: x86_64 oder aarch64, Administratorrechte, DNF/RPM, curl, gpg und CA-Zertifikate. Installieren Sie fehlende Werkzeuge aus Ihrer Distribution. Prüfen Sie vor dem Import den Schlüssel und vergleichen Sie den obigen Fingerabdruck:

curl -fsSL https://www.versionx.ai/rpm/gpg.key -o versionx-rpm.asc
gpg --show-keys --with-fingerprint versionx-rpm.asc
sudo rpm --import versionx-rpm.asc
sudo tee /etc/yum.repos.d/versionx.repo >/dev/null <<'EOF'
[versionx]
name=VersionX ash repository
baseurl=https://www.versionx.ai/rpm/
enabled=1
gpgcheck=0
repo_gpgcheck=1
gpgkey=https://www.versionx.ai/rpm/gpg.key
EOF
sudo dnf install ash
rm versionx-rpm.asc

RPM-Dateien sind nicht einzeln signiert. repo_gpgcheck=1 prüft Repository-Metadaten mit ihren Prüfsummen; gpgcheck=0 entspricht fehlenden Paketsignaturen, nicht deaktivierter Repository-Prüfung. Verlangt Ihre Richtlinie signierte RPM-Nutzdaten, erfüllt dieses Repository sie nicht. Aktualisieren: sudo dnf upgrade ash; entfernen: sudo dnf remove ash.

Arch Linux: Pacman

Voraussetzungen: x86_64, Administratorrechte, Pacman mit initialisiertem Schlüsselbund, curl und gpg. Vertrauen Sie dem Schlüssel erst, wenn sein angezeigter Fingerabdruck dem obigen entspricht. Fügen Sie das Repository einmal hinzu, nicht bei jedem Update:

curl -fsSL https://www.versionx.ai/pacman/gpg.key -o versionx-pacman.asc
gpg --show-keys --with-fingerprint versionx-pacman.asc
sudo pacman-key --add versionx-pacman.asc
sudo pacman-key --lsign-key 32C6C11D2F86BFE46EB77FFC5257FEA61368919F
sudo tee -a /etc/pacman.conf >/dev/null <<'EOF'
[versionx]
Server = https://www.versionx.ai/pacman/$arch
SigLevel = Required DatabaseRequired
EOF
sudo pacman -Syu ash
rm versionx-pacman.asc

Pacman prüft Paket- und Datenbanksignaturen. Halten Sie Arch mit sudo pacman -Syu synchron, statt teilweise zu aktualisieren; entfernen Sie ash mit sudo pacman -R ash.

Weitere Linux-Installationsmethoden

Nutzen Sie bereits Homebrew unter Linux? Die gleichen Tap-Anweisungen unterstützen amd64 und arm64; Brew verwaltet diese Dateien, nicht APT/DNF. Andernfalls verwenden Sie eine verifizierte Skript-/Archivinstallation oder einen passenden .deb-/.rpm-Download. Installieren Sie ein verifiziertes .deb mit sudo apt install ./PACKAGE.deb, ein .rpm mit sudo dnf install ./PACKAGE.rpm (Dateinamen ersetzen). Direkte Pakete bleiben paketverwaltet, fügen aber kein Repository oder Abonnement künftiger Versionen hinzu. Aktuelle RPM-Nutzdaten sind unsigniert; befolgen Sie die Distributionsrichtlinie, statt Signaturprüfungen abzuschalten.

FreeBSD

Voraussetzungen: amd64, Bash (auch mit interaktivem zsh oder Fish), Download-/Prüfwerkzeuge und ein beschreibbares Installationsverzeichnis. Installieren Sie Bash mit FreeBSDs nativer Paketverwaltung:

sudo pkg install bash

FreeBSDs pkg verwaltet Voraussetzungen, nicht ash: derzeit existieren weder ash-.pkg-Repository noch arm64-Versionsarchiv. Verwenden Sie das verifizierte Skript oder prüfen Sie ein FreeBSD-amd64-Tarball, entpacken Sie es in ein temporäres Verzeichnis und installieren Sie dessen versionierte ash-Binärdatei als ~/.local/bin/ash neben ash-broker. Kopieren Sie native Plugins nach $XDG_DATA_HOME/ash/plugins (Standard: ~/.local/share/ash/plugins), dann initialisieren. Sie verwalten diese Dateien; pkg delete entfernt sie nicht. Nutzen Sie am Standardort Release-Selbstupdates oder ersetzen Sie verifizierte Dateien manuell.

Initialisieren und prüfen

Führen Sie nach Installation der Binärdateien die Einrichtung interaktiv als normaler Benutzer aus. Eine reine Dateieinrichtung lässt Startdateien unverändert:

ash install

Für die Integration unbekannter Befehle wählen Sie genau einen Befehl für Ihre Shell:

Bash

ash install --shell bash --shell-integration

zsh

ash install --shell zsh --shell-integration

Fish

ash install --shell fish --shell-integration

Bash verwendet ~/.bashrc, zsh ~/.zshrc und Fish $XDG_CONFIG_HOME/fish/config.fish (Standard: ~/.config/fish/config.fish). Öffnen Sie anschließend eine neue Shell; vorhandene Shells behalten ihren laufenden Broker. Die Integration stellt ~/.local/bin dem PATH voran: entfernen Sie alte benutzerlokale Kopien, bevor Sie die Auswahl eines Systempakets erwarten.

Fehlen Anbietereinstellungen, erkennt die Einrichtung vorhandene Schlüssel oder laufende lokale Server; andernfalls zeigt sie ein Anbietermenü und fragt Zugangsdaten ab. Wählen Sie ein verfügbares Modell mit Werkzeugaufrufen. Gültige Einstellungen bleiben erhalten; erneutes Einrichten ist kein Anbieterwechsel.

Einstellungen liegen in $XDG_CONFIG_HOME/ash/.ash_env (Standard: ~/.config/ash/.ash_env, private Dateirechte). Die verwaltete Integration lädt sie. Ohne Integration können Bash/zsh-Benutzer diese Datei in ihrer Startkonfiguration einlesen; Fish-Benutzer setzen entsprechende ASH_AI_*-Variablen mit Fish-Syntax, statt die Bash-Datei einzulesen. Schützen Sie Dateien mit Tokens und committen Sie sie niemals.

Ohne Integration fügen Sie das tatsächliche benutzerlokale Installationsverzeichnis dem PATH hinzu. Bash/zsh: export PATH="$HOME/.local/bin:$PATH". Fish: fish_add_path "$HOME/.local/bin". Speichern Sie dies in der Shell-Startkonfiguration; ersetzen Sie gegebenenfalls das Verzeichnis durch Ihren eigenen Installationsort.

command -v ash
command -v ash-broker
ash version
ash "Say hello in one sentence"

Die ersten Befehle müssen die gewählte Installation finden. Die Anfrage benötigt einen laufenden Server oder gültige Cloud-Zugangsdaten; ash installiert kein Modell.

Lokales Ollama: kein Cloud-Konto erforderlich

Installieren Sie Ollama nach seinen offiziellen Betriebssystemanweisungen. Starten Sie die Ollama-App/den Dienst oder ollama serve in einem separaten Terminal, falls noch kein Server läuft. ash-Unterstützung auf FreeBSD bedeutet keinen nativen Ollama-Installer: nutzen Sie bei Bedarf einen erreichbaren Server auf einem anderen unterstützten Rechner.

Laden Sie ein zu Ihrer Hardware passendes Modell mit Werkzeugaufrufen; llama3.1:8b ist ein Beispiel, keine Mindestanforderung. Alternativen stehen im aktuellen Werkzeugkatalog:

ollama pull llama3.1:8b
ollama list
curl -fsS http://localhost:11434/api/tags
ash install

Ohne bereits gesetzte Cloud-Schlüssel erkennt die Einrichtung den lokalen Server und bietet das geladene Modell an. Ist schon ein anderer Anbieter konfiguriert, ändern Sie Endpunkt/Modell manuell. Bash/zsh-Beispiel:

export ASH_AI_ENDPOINT="http://localhost:11434"
export ASH_AI_MODEL="llama3.1:8b"
unset ASH_AI_AUTH_TOKEN
ash "Say hello in one sentence"

Entsprechung für Fish:

set -gx ASH_AI_ENDPOINT http://localhost:11434
set -gx ASH_AI_MODEL llama3.1:8b
set -e ASH_AI_AUTH_TOKEN
ash "Say hello in one sentence"

Diese Änderungen gelten nur für die aktuelle Shell. Speichern Sie sie in Ihrer geschützten ash-Umgebungsdatei oder geeigneten Shell-Konfiguration und ersetzen Sie alte Anbieterüberschreibungen. Lokales Ollama benötigt kein Token. Lassen Sie den Server auf Loopback, außer Sie sichern den Zugriff bewusst ab; entfernte Server erhalten Ihre Anfragen und Werkzeugausgaben.

Optional: setzen Sie OLLAMA_KEEP_ALIVE=30m in der Umgebung des Ollama-Servers und starten Sie ihn neu, um Modelle geladen zu halten. -1 hält sie unbegrenzt geladen, verbraucht aber zwischen Anfragen Speicher. Nur im ash-Clientterminal gesetzt, konfiguriert dies keinen bereits laufenden Server neu.

Lokale Inferenz verursacht keine Anbieter-API-Rechnung, nutzt aber Hardware/Speicher/Strom. Ollama Cloud ist ein separater Dienst mit Authentifizierung und Tarifgrenzen, nicht diese lokale Einrichtung.

Kostenlose Cloud-Tarife

Kostenlos bedeutet weder unbegrenzt noch privat. Konten, Regionen, Kontingente, verfügbare Modelle und Datenrichtlinien unterscheiden und ändern sich. Anfragen und relevante Werkzeugausgaben verlassen Ihren Rechner. Prüfen Sie aktuelle Grenzen und Bedingungen; aktivieren Sie bezahlte Abrechnung nur, wenn Sie zahlen wollen.

Erstellen Sie über die folgenden Links einen Anbieterschlüssel, führen Sie ash install interaktiv aus und wählen Sie den Anbieter. Die Einrichtung fragt das Token ab und listet, soweit unterstützt, Modelle. Wählen Sie ein aktuell kostenlos verfügbares Textmodell mit Werkzeugaufrufen; eine Auflistung garantiert keine kostenlose Nutzung für Ihr Konto.

Manuelle Konfiguration oder Anbieterwechsel

Ersetzen Sie den folgenden Endpunkt durch den Tabellenwert und MODEL_ID durch ein in Ihrem Anbieterkonto geprüftes Modell. Ist Ihr Schlüssel bereits als GROQ_API_KEY exportiert, nutzt dieses Bash/zsh-Beispiel ihn ohne Eingabe des Geheimnisses:

export ASH_AI_ENDPOINT="https://api.groq.com/openai/v1"
export ASH_AI_MODEL="MODEL_ID"
export ASH_AI_AUTH_TOKEN="$GROQ_API_KEY"

Entsprechung für Fish:

set -gx ASH_AI_ENDPOINT https://api.groq.com/openai/v1
set -gx ASH_AI_MODEL MODEL_ID
set -gx ASH_AI_AUTH_TOKEN "$GROQ_API_KEY"

Für Gemini/OpenRouter verwenden Sie deren Endpunkt und erkannte Schlüsselvariable. Speichern Sie die gewählten Einstellungen sicher für spätere Shells. Cloud-Endpunkte benötigen HTTPS und Token; lokales HTTP ist keine Abkürzung zum Cloud-Dienst. Siehe Umgebungsreferenz und weitere unterstützte Anbieter für Bezahldienste und erweiterte Überschreibungen.

Skriptinstallation: Alternative, nicht erste Wahl

Bevorzugen Sie Homebrew, APT, DNF oder Pacman: sie verfolgen verwaltete Dateien, prüfen Downloads anhand ihrer Vertrauenskonfiguration und bieten vertraute Updates/Entfernung. Dennoch müssen Sie Herausgebern und Paketinstallationsaktionen vertrauen.

Ein Website-Skript führt Code mit Ihren Kontorechten aus. Kompromittierte Websites, Herausgeber oder veränderte Skripte können Geheimnisse lesen, Dateien ändern oder andere Software installieren. HTTPS schützt den Transport, nicht die Absichten des Codes. Direktes Weiterleiten einer URL an eine Shell führt Code vor der Prüfung aus. Archivsignaturprüfungen authentifizieren nicht das Skript selbst. Verwenden Sie niemals sudo und deaktivieren Sie nie dessen Prüfung.

Voraussetzungen: unterstütztes Betriebssystem/Architektur, $SHELL mit Bash/zsh/Fish, Sigstore cosign, tar, uname, install, Standard-Shellwerkzeuge, SHA-256-Befehl (sha256sum, shasum oder sha256) und Downloadwerkzeug (curl, wget oder Python). Das Beispiel nutzt curl. FreeBSD benötigt außerdem Bash. Home-/Installationsverzeichnis müssen beschreibbar sein.

Laden Sie eine lokale Datei, prüfen Sie sie im Editor und führen Sie sie nur bei Vertrauen in Quelle und Verhalten aus. Prüfung garantiert keine Sicherheit; führen Sie diese Schritte nicht blind aus:

curl -fsSL https://jonconradt.github.io/ash/install.sh -o ash-install.sh
less ash-install.sh

Nach der Prüfung starten Sie die gespeicherte Kopie als normaler Benutzer:

sh ./ash-install.sh
rm ./ash-install.sh

install.sh lädt das neueste Release, prüft dessen Sigstore-signiertes Prüfsummenmanifest und Archivdigest und installiert ash/ash-broker in ~/.local/bin. Native Plugins liegen unter $XDG_DATA_HOME/ash/plugins. Es richtet benutzerspezifische Dateien ein und fragt vor Shell-Integration. Ohne interaktives Terminal können Anbieter-/Integrationsfragen entfallen: führen Sie anschließend ash install interaktiv aus.

Mit ASH_INSTALL_DIR vor dem Skriptstart wählen Sie einen anderen Zielort. Fügen Sie ihn selbst dem PATH hinzu. Selbstupdates werden nur unter ~/.local/bin unterstützt; andere Ziele erfordern manuelles Ersetzen. Das Skript hat keine Beta-/Nightly-Auswahl.

Direktes Paket oder Archiv verifizieren

Voraussetzungen: cosign und SHA-256-Werkzeug. Laden Sie Paket/Archiv, SHA256SUMS und SHA256SUMS.sigstore.json aus derselben veröffentlichten Version. Arbeiten Sie in einem neuen Verzeichnis. Ersetzen Sie vX.Y.Z durch das genaue Tag einschließlich eventuellem Vorabversionssuffix:

cosign verify-blob SHA256SUMS \
  --bundle SHA256SUMS.sigstore.json \
  --certificate-identity "https://github.com/Jonconradt/ash/.github/workflows/release.yml@refs/tags/vX.Y.Z" \
  --certificate-oidc-issuer "https://token.actions.githubusercontent.com"

Erst nach Erfolg berechnen Sie den Dateidigest mit shasum -a 256 PACKAGE auf macOS, sha256sum PACKAGE auf Linux oder sha256 -q PACKAGE auf FreeBSD. Ersetzen Sie PACKAGE durch den Download-Dateinamen und vergleichen Sie exakt mit dessen Eintrag im verifizierten Manifest. Bei fehlendem Eintrag oder Abweichung abbrechen. Eine neben der Datei heruntergeladene unsignierte Prüfsumme ist keine verifizierte Herausgebermetadatenprüfung.

Updates und die drei Kanäle

  • Release (empfohlen): stabile Veröffentlichungen wie vX.Y.Z; die Repository-Konfiguration nennt sie stable.
  • Beta: Vorabtests mit Tag vX.Y.Z-beta.N; Änderungen und Regressionen sind zu erwarten.
  • Nightly: aktuelle Änderungen des Standardbranches, Tag vX.Y.Z-nightly.YYYYMMDD.N; höchstes Regressionsrisiko. Builds sind geplant, können aber ohne Änderungen oder bei Veröffentlichungsfehlern ausfallen.

Eine Veröffentlichung aktualisiert die zugehörige Homebrew-Formel oder das signierte Linux-Repository. Sie erhalten sie durch den Upgrade-Befehl der zuständigen Verwaltung oder Ihre Betriebssystem-Updaterichtlinie. Veröffentlichung, Repository und Website können zeitlich auseinanderliegen; prüfen Sie Verfügbarkeit vor Kanalwechseln. ash installiert keine stillen Hintergrund-Binärupdates.

Homebrew: Formeln installieren oder wechseln

Für neue Beta-/Nightly-Installationen verwenden Sie den vollständigen Formelnamen aus der Tabelle in brew install. Deinstallieren Sie beim Wechsel zuerst die aktuelle Formel: alle drei liefern dieselben Binärdateien. Beispiel Release zu Beta:

brew uninstall ash
brew install Jonconradt/ash/ash-beta
brew update
brew upgrade ash-beta

Verwenden Sie in Installations-/Upgrade-Befehlen ash-nightly für Nightly oder ash für Release. Entfernen Sie die tatsächliche alte Kanalformel, nicht immer ash. Benutzereinstellungen bleiben erhalten; öffnen Sie danach eine neue Shell.

Linux: einen Repository-Kanal wählen

APT: verwenden Sie die APT-Einrichtung mit genau einer Tabellendistribution. Zum Wechsel bearbeiten Sie /etc/apt/sources.list.d/versionx.list, ersetzen stable durch beta oder nightly (oder zurück durch stable), dann:

sudo apt update
sudo apt install --allow-downgrades ash

DNF: verwenden Sie die DNF-Einrichtung mit gewählter baseurl. Ersetzen Sie bei vorhandener Installation baseurl in /etc/yum.repos.d/versionx.repo, behalten Sie Signaturparameter bei, dann:

sudo dnf --refresh distro-sync ash

Pacman: verwenden Sie die Pacman-Einrichtung mit gewählter Server-URL. Behalten Sie den Abschnittsnamen [versionx]: jeder Kanal veröffentlicht versionx.db. Ändern Sie Server in diesem Abschnitt, statt eine anders benannte Datenbank hinzuzufügen. Wechsel einschließlich Downgrade:

sudo pacman -Syuu ash

Prüfen Sie die vorgeschlagene Transaktion: die Rückkehr zu Release kann ash herunterstufen, Pacmans doppeltes u auch andere Pakete. Sichern Sie vor dem Wechsel die Konfiguration. Nutzen Sie danach normale APT-/DNF-/Pacman-Upgrades aus den Betriebssystemabschnitten; lassen Sie nicht mehrere ash-Kanalquellen aktiviert.

Benutzerlokale Release-Updates

ash update

Dies prüft und installiert stabile Releases nur, wenn die aktive ash-Datei unter ~/.local/bin liegt. Mitgelieferte Dateien/Plugins werden ebenfalls aktualisiert, mit Auswahl für angepasste Dateien. ash update --version vX.Y.Z wählt ein stabiles Tag, keinen Kanal; es ist kein Downgrade-Befehl. Eine --channel-Option existiert nicht. Paketverwaltete, macOS-.pkg- und benutzerdefinierte Skriptinstallationen verwenden stattdessen ihre zuständige Verwaltung/Installer. FreeBSD Beta/Nightly nutzt manuelle verifizierte Archive, kein Selbstupdate-Abonnement. Öffnen Sie danach eine neue Shell.

Deinstallieren ohne fremde Dateien zu löschen

1. Zuerst Shell-Integration deaktivieren

Führen Sie vor dem Löschen der Binärdateien den Befehl für jede Shell mit aktivierter Integration aus:

Bash

ash install --shell bash --disable-shell-integration

zsh

ash install --shell zsh --disable-shell-integration

Fish

ash install --shell fish --disable-shell-integration

Fehlt ash bereits, bearbeiten Sie die passende Startdatei aus Initialisierung und entfernen nur den Block zwischen # >>> ash install >>> und # <<< ash install <<<. Entfernen Sie manuell ergänzte ash-PATH-/Umgebungszeilen, nicht sonstige Shell-Konfiguration. Schließen Sie danach ash-Shells, damit deren Broker enden.

2. Die zuständige Paketverwaltung entfernt ihre Dateien

Homebrew (Release)

brew uninstall ash

APT

sudo apt remove ash

DNF

sudo dnf remove ash

Pacman

sudo pacman -R ash

Wählen Sie nur Ihre Installationsmethode; für Homebrew Beta/Nightly nutzen Sie ash-beta/ash-nightly. APT/DNF/Pacman entfernen verwaltete Binärdateien, Plugins und Handbuchseiten, nicht Konfiguration/Verlauf im Home-Verzeichnis. Löschen Sie paketverwaltete Dateien nicht manuell.

Optionale Repository-Bereinigung: entfernen Sie die ash-Quelldatei /etc/apt/sources.list.d/versionx.list und ihren eigenen /etc/apt/keyrings/versionx-keyring.gpg, die Repository-Datei /etc/yum.repos.d/versionx.repo oder den ash-Abschnitt [versionx] aus /etc/pacman.conf. Prüfen Sie zuerst, dass andere Pakete sie nicht verwenden. Löschen Sie importierte RPM-/Pacman-Schlüssel erst nach Fingerabdruckprüfung und wenn nichts anderes sie benötigt; nie den gemeinsamen Schlüsselbund einer Distribution löschen.

3a. macOS-.pkg manuell entfernen

macOS Installer speichert einen Beleg, hat aber keinen ash-Deinstaller. Stellen Sie sicher, dass es eine .pkg-Installation und nicht Homebrew ist, und prüfen Sie die genaue Dateiliste:

pkgutil --pkg-info dev.ash.cli
pkgutil --files dev.ash.cli

Entfernen Sie anhand des Belegs nur ash-Dateien: /usr/local/bin/ash, /usr/local/bin/ash-broker, Dateien in /usr/local/lib/ash/plugins, /usr/local/share/man/man1/ash.1, aufgeführte lokalisierte ash.1-Seiten und Hinweise in /usr/local/share/licenses/ash. Administratorrechte sind nötig. Hat ein anderer Installer sie inzwischen ersetzt, prüfen Sie die Zuständigkeit und löschen Sie nicht dessen Kopie. Entfernen Sie leere reine ash-Verzeichnisse, keine gemeinsamen /usr/local-, bin- oder man-Verzeichnisse.

Nach Entfernen der Dateien können Sie optional den Beleg entfernen:

sudo pkgutil --forget dev.ash.cli

Das Vergessen eines Belegs löscht keine installierten Dateien. Bewahren Sie ihn bis zur abgeschlossenen Dateiprüfung auf.

3b. Benutzerlokale / Linux- / FreeBSD-Archive manuell entfernen

Finden Sie die aktive Kopie mit command -v ash und command -v ash-broker. Entfernen Sie bei der Standardskriptinstallation nach Hook-Deaktivierung genau diese beiden Dateien:

rm "$HOME/.local/bin/ash" "$HOME/.local/bin/ash-broker"

Für ASH_INSTALL_DIR oder manuell entpackte Archive löschen Sie nur tatsächliche ash-/Broker-Pfade. Entfernen Sie installierte Archivplugins/Handbuchseiten/Hinweise anhand der ursprünglichen Dateiliste; Skriptplugins liegen im ash-Benutzerdatenverzeichnis. Prüfen Sie bei Dateien unter /usr/bin zuerst die Zuständigkeit mit dpkg -S /usr/bin/ash, rpm -qf /usr/bin/ash oder pacman -Qo /usr/bin/ash. Paketverwaltete Kopien müssen selbst bei Einzeldownloads durch ihre Verwaltung entfernt werden.

4. Optional: lokale Einstellungen, Werkzeuge und Verlauf löschen

Sichern Sie alles, was Sie behalten möchten. Dieser separate Schritt kann Anbietereinstellungen/Tokens, eigene Werkzeuge/Plugins, Gesprächsverlauf und Arbeitsdateien löschen. Binärdateien zu deinstallieren bedeutet keine Zustimmung dazu.

  • Konfiguration: $XDG_CONFIG_HOME/ash, Standard ~/.config/ash.
  • Daten, Plugins und Python-Umgebung: $XDG_DATA_HOME/ash, Standard ~/.local/share/ash.
  • Verlauf und Zustand: $XDG_STATE_HOME/ash, Standard ~/.local/state/ash.
  • Cache: $XDG_CACHE_HOME/ash, Standard ~/.cache/ash.
  • Broker-Laufzeit: $XDG_RUNTIME_DIR/ash, oder $XDG_STATE_HOME/ash/runtime, wenn kein Laufzeitstamm verfügbar ist.

Prüfen Sie tatsächliche absolute XDG-Überschreibungen, bevor Sie nur diese ash-Unterverzeichnisse löschen; nie XDG-Stamm oder Home-Verzeichnis löschen. Entfernen Sie bei Bedarf Laufzeitreste erst nach Schließen aller ash-Shells. MCP-OAuth-Zugangsdaten können in der Betriebssystem-Zugangsdatenverwaltung verbleiben: entfernen Sie ash-Einträge und widerrufen Sie Zugriff beim MCP-Anbieter. Widerrufen Sie unbenutzte KI-Schlüssel beim Anbieter; lokale Löschung widerruft keinen Schlüssel. Entfernen Sie nicht zugleich Ollama/Modelle, Python oder gemeinsame Abhängigkeiten.

Kurze Fehlerbehebung

Befehl fehlt oder falsche Version
Prüfen Sie PATH und command -v ash/command -v ash-broker. Alte Kopien in ~/.local/bin können Pakete verdecken. Verwenden Sie jeweils nur eine Verwaltung/einen Kanal und öffnen Sie eine neue Shell.
Anbietermenü fehlt
Führen Sie ash install interaktiv aus. Gültige Einstellungen bleiben erhalten; zum Wechsel nutzen Sie manuelle Konfiguration. Ohne Integration müssen Einstellungen in die CLI-Umgebung exportiert sein.
Kein Modell oder Verbindung abgelehnt
Prüfen Sie für Ollama, dass der Server läuft und ollama list Ihr Modell enthält. Prüfen Sie bei Cloud-Diensten Endpunkt, Modellberechtigung, HTTPS, Token und Kontingent; teilen Sie nie Logs mit Tokens.
Repository oder Kanal nicht verfügbar
Prüfen Sie Architektur und veröffentlichte Version/Repository. Veröffentlichungen können sich verzögern; deaktivieren Sie nie Signaturprüfung als Umgehung.
Einrichtung der Python-Werkzeuge fehlgeschlagen
Installieren Sie Python mit venv/ensurepip, erlauben Sie Abhängigkeitsdownloads und starten Sie ash install erneut. Grundlegendes ash bleibt ohne diese Werkzeuge nutzbar.
