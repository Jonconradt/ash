Bevor Sie beginnen

  1. Ein unterstütztes System und eine unterstützte Shell: macOS oder Linux auf amd64/x86_64 oder arm64/aarch64 oder FreeBSD auf amd64. Verwenden Sie Bash, ZSH oder Fish. Arch-Pakete sind nur x86_64. Es gibt kein natives Windows/PowerShell-Installationsprogramm.
  2. Download-Zugriff: eine funktionierende Internetverbindung und vertrauenswürdiger HTTPS-Zugriff auf GitHub, das ausgewählte Paket-Repository und Ihren Modellanbieter. Lokale Inferenz erfordert noch einen ersten Modell-Download.
  3. Berechtigungen: ein beschreibbares Home-Verzeichnis für Assets pro Benutzer. Linux-Systempakete und macOS .pkg benötigen Administratorzugriff; Führen Sie Homebrew und ash install als Ihr normaler Benutzer aus.
  4. Ein Modell: entweder ein lokaler Inferenzserver mit einem heruntergeladenen Modell oder ein Cloud-Konto/API-Schlüssel. Wählen Sie ein Modell, das Toolaufrufe unterstützt, und kein reines Bild-/Audiomodell. Die lokalen RAM-, Festplatten- und GPU-Anforderungen hängen von diesem Modell ab.

Vorgefertigte ash-Pakete erfordern keine Go-, Rust-, Node.js- oder Xcode-Build-Tools. Ein Paketmanager kann seine eigenen Voraussetzungen haben; Befolgen Sie zunächst die offiziellen Einrichtungsanweisungen.

Unter Debian/Ubuntu installierenpython3Undpython3-venv; Homebrew Python beinhaltet Venv-Unterstützung. Verwenden Sie unter FreeBSD das Pip-Paket, das zu Ihrer Python-Version passt. Dann erneut ausführenash install. Setup erstellt eine isolierte Umgebung unter$XDG_DATA_HOME/ash/venv(Standard~/.local/share/ash/venv); Ein Fehler deaktiviert diese Tools, nicht die grundlegendenash.

Debian und Ubuntu: APT

Voraussetzungen: amd64 oder arm64, Administratorzugriff, APT,curl,gpgund CA-Zertifikate. Installieren Sie fehlende Download-/Schlüsseltools mit Ihrer Distribution, bevor Sie das Repository hinzufügen. Die Veröffentlichung ist benanntstable:

sudo apt update
sudo apt install ca-certificates curl gnupg
sudo install -d -m 0755 /etc/apt/keyrings
curl -fsSL https://www.versionx.ai/apt/gpg.key -o versionx-apt.asc
gpg --show-keys --with-fingerprint versionx-apt.asc
sudo gpg --dearmor --batch --yes -o /etc/apt/keyrings/versionx-keyring.gpg versionx-apt.asc
sudo chmod 0644 /etc/apt/keyrings/versionx-keyring.gpg
echo "deb [signed-by=/etc/apt/keyrings/versionx-keyring.gpg] https://www.versionx.ai/apt stable main" |
  sudo tee /etc/apt/sources.list.d/versionx.list
sudo apt update
sudo apt install ash
rm versionx-apt.asc

Bevor Sie einen Repository-Schlüssel importieren, überprüfen Sie dessen Fingerabdruck anhand einer vertrauenswürdigen Herausgeberquelle. Der Fingerabdruck des VersionX-Schlüssels ist32C6 C11D 2F86 BFE4 6EB7 7FFC 5257 FEA6 1368 919F. APT prüft signierte Repository-Metadaten und die darin enthaltenen Paket-Digests; Der Schlüssel hat einen Gültigkeitsbereichsigned-by. Update mitsudo apt update && sudo apt upgrade ash; mit entfernensudo apt remove ash.

Fedora- und RHEL-kompatible Systeme: DNF

Voraussetzungen: x86_64 oder aarch64, Administratorzugriff, DNF/RPM,curl,gpgund CA-Zertifikate. Installieren Sie fehlende Tools aus Ihrer Distribution. Überprüfen Sie den Schlüssel und vergleichen Sie den Fingerabdruck oben, bevor Sie ihn importieren:

curl -fsSL https://www.versionx.ai/rpm/gpg.key -o versionx-rpm.asc
gpg --show-keys --with-fingerprint versionx-rpm.asc
sudo rpm --import versionx-rpm.asc
sudo tee /etc/yum.repos.d/versionx.repo >/dev/null <<'EOF'
[versionx]
name=VersionX ash repository
baseurl=https://www.versionx.ai/rpm/
enabled=1
gpgcheck=0
repo_gpgcheck=1
gpgkey=https://www.versionx.ai/rpm/gpg.key
EOF
sudo dnf install ash
rm versionx-rpm.asc

RPM-Dateien werden nicht einzeln signiert.repo_gpgcheck=1überprüft Repository-Metadaten, die ihre Prüfsummen abdecken;gpgcheck=0spiegelt die fehlenden Signaturen pro Paket wider, nicht die deaktivierte Repository-Überprüfung. Wenn Ihre Richtlinie signierte RPM-Nutzlasten erfordert, erfüllt dieses Repository diese nicht. Update mitsudo dnf upgrade ash; mit entfernensudo dnf remove ash.

Arch Linux: Pacman

Voraussetzungen: x86_64, Administratorzugriff, Pacman mit initialisiertem Schlüsselbund,curl, Undgpg. Stellen Sie sicher, dass der angezeigte Fingerabdruck des Schlüssels mit dem oben genannten übereinstimmt, bevor Sie ihm vertrauen. Fügen Sie das Repository einmal hinzu, nicht bei jedem Update:

curl -fsSL https://www.versionx.ai/pacman/gpg.key -o versionx-pacman.asc
gpg --show-keys --with-fingerprint versionx-pacman.asc
sudo pacman-key --add versionx-pacman.asc
sudo pacman-key --lsign-key 32C6C11D2F86BFE46EB77FFC5257FEA61368919F
sudo tee -a /etc/pacman.conf >/dev/null <<'EOF'
[versionx]
Server = https://www.versionx.ai/pacman/$arch
SigLevel = Required DatabaseRequired
EOF
sudo pacman -Syu ash
rm versionx-pacman.asc

Pacman überprüft sowohl Paket- als auch Datenbanksignaturen. Halten Sie Arch synchron mitsudo pacman -Syu, kein teilweises Upgrade; entfernenashmitsudo pacman -R ash.

Initialisieren und überprüfen

Nach der Installation der Binärdateien führen Sie das Setup interaktiv als Ihr normaler Benutzer aus. Wenn Sie keine Shell-Integration wünschen, können Sie nur Ash installieren. Das ist wahrscheinlich nicht das, was Sie wollen. Der wahre Wert von ash ist die Shell-Integration unten. Bei der Nur-Asset-Einrichtung bleiben Ihre Startdateien unverändert:

ash install

Die Installation, die Sie wahrscheinlich verwenden möchten, beinhaltet die Shell-Integration. Dadurch wird Ihr .bashrc (oder das Äquivalent für Ihre Shell) so geändert, dass er Ash enthält. Um die Integration von nicht gefundenen Befehlen zu aktivieren, wählen Sie genau einen Befehl für die von Ihnen verwendete Shell aus:

Bash

ash install --shell bash --shell-integration

zsh

ash install --shell zsh --shell-integration

Fisch

ash install --shell fish --shell-integration

Bash verwendet~/.bashrc, zsh verwendet~/.zshrc, und Fisch verwendet$XDG_CONFIG_HOME/fish/config.fish(Standard~/.config/fish/config.fish). Öffnen Sie anschließend eine neue Shell. Bestehende Shells behalten ihren laufenden Broker. Integration steht im Vordergrund~/.local/binzu PATH: Entfernen Sie eine alte benutzerlokale Kopie, bevor Sie erwarten, dass ein Systempaket ausgewählt wird.

Wenn Anbietereinstellungen fehlen, erkennt das Setup vorhandene Anbieterschlüssel oder einen laufenden lokalen Server. andernfalls bietet es ein Anbietermenü und fordert zur Eingabe von Anmeldeinformationen auf. Wählen Sie ein verfügbares, werkzeugfähiges Modell. Vorhandene gültige Einstellungen bleiben erhalten, daher ist die erneute Ausführung des Setups kein Befehl zum Anbieterwechsel.

Die Einstellungen werden in gespeichert$XDG_CONFIG_HOME/ash/.ash_env(Standard~/.config/ash/.ash_env, private Dateiberechtigungen). Die verwaltete Integration lädt sie. Ohne Integration können Bash/zsh-Benutzer diese Datei in ihrer normalen Startkonfiguration als Quelle verwenden; Fischbenutzer sollten das entsprechende einstellenASH_AI_*Variablen mithilfe der Fish-Syntax, nicht als Quelle der Bash-Formatdatei. Schützen Sie alle Dateien, die Token enthalten, und schreiben Sie sie niemals fest.

Für eine benutzerlokale Installation ohne Integration fügen Sie das tatsächliche Verzeichnis zu PATH hinzu. Bash/zsh:export PATH="$HOME/.local/bin:$PATH". Fisch:fish_add_path "$HOME/.local/bin". Behalten Sie dies bei, indem Sie die Startkonfiguration Ihrer Shell verwenden. Ersetzen Sie gegebenenfalls Ihr benutzerdefiniertes Installationsverzeichnis.

command -v ash
command -v ash-broker
ash version
ash "Say hello in one sentence"

Die ersten Befehle sollten sich auf die von Ihnen gewählte Installation beziehen. Für die Eingabeaufforderung sind ein laufender Server oder gültige Cloud-Anmeldeinformationen erforderlich. Durch die Installation von ash wird kein Modell installiert.

Lokales Ollama: kein Cloud-Konto erforderlich

Sie benötigen keine lokale KI, um sie verwenden zu könnenash. Wenn Sie Modelle jedoch lokal ausführen möchten, ohne auf einen Cloud-Anbieter angewiesen zu sein, können Sie einen lokalen Ollama-Server einrichten.

Ollama bietet auch einen Cloud-Dienst für die Remote-Ausführung von Modellen an, dieser ist jedoch für die lokale Nutzung nicht erforderlichash. Der Cloud-Server umfasst eine kostenlose Stufe und das Cloud-Modell Gemma 4 31b von Google (gemma4-31b:cloud) funktioniert sehr gut mitash. Dies ist das Modell, das das Projekt zum Generieren von Versionshinweisen und zum Ausführen von Entwicklungsaufgaben verwendet.

Installieren Sie Ollama mit dessenoffizielle Betriebssystemanweisungen. Starten Sie die Ollama-App/den Ollama-Dienst oder führen Sie sie ausollama servein einem separaten Terminal, wenn noch kein Server läuft. Auf FreeBSD,ashDie Unterstützung von 's bedeutet nicht, dass es sich um ein natives Ollama-Installationsprogramm handelt: Verwenden Sie bei Bedarf einen erreichbaren Server auf einem anderen unterstützten Host.

Laden Sie ein werkzeugfähiges Modell herunter, das zu Ihrer Hardware passt.llama3.1:8bist ein Beispiel und keine Mindestanforderung. Überprüfen Sie dieAktueller Werkzeugkatalogfür Alternativen:

Wenn noch keine Cloud-Schlüssel festgelegt sind, kann das Setup den lokalen Server erkennen und das heruntergeladene Modell anbieten. Wenn bereits ein anderer Anbieter konfiguriert ist, ändern Sie stattdessen den Endpunkt/das Modell manuell. Bash/zsh-Beispiel:

export ASH_AI_ENDPOINT="http://localhost:11434"
export ASH_AI_MODEL="llama3.1:8b"
unset ASH_AI_AUTH_TOKEN

Fischäquivalent:

set -gx ASH_AI_ENDPOINT http://localhost:11434
set -gx ASH_AI_MODEL llama3.1:8b

Diese Änderungen betreffen nur die aktuelle Shell. Behalten Sie sie in Ihrem Schutz beiashUmgebungsdatei oder entsprechende Shell-Konfiguration und ersetzt alle alten Anbieterüberschreibungen. Das lokale Ollama benötigt keinen Token. Lassen Sie den Server auf Loopback, es sei denn, Sie sichern den Zugriff absichtlich ab. Ein Remote-Server empfängt Ihre Eingabeaufforderungen und Tool-Ausgaben.

Skriptinstallation: eine Alternative, nicht die erste Wahl

Bevorzugen Sie Homebrew, APT, DNF oder Pacman: Sie verfolgen eigene Dateien, überprüfen Downloads mithilfe ihrer Vertrauenskonfiguration und bieten vertraute Updates/Entfernungen. Sie erfordern weiterhin vertrauenswürdige Herausgeber und Paketinstallationsaktionen.

Ein Website-Skript führt Code mit den Berechtigungen Ihres Kontos aus. Eine kompromittierte Website, ein kompromittierter Herausgeber oder ein sich änderndes Skript kann Geheimnisse lesen, Dateien ändern oder andere Software installieren. HTTPS schützt den Transport, nicht die Absichten dieses Codes. Wenn Sie eine URL direkt an eine Shell weiterleiten, wird sie ausgeführt, bevor Sie sie überprüfen können. Die Archivsignaturprüfungen des Skripts authentifizieren das Skript selbst nicht. Führen Sie es niemals mit sudo aus oder deaktivieren Sie die Überprüfung.

Voraussetzungen: ein unterstütztes Betriebssystem/eine unterstützte Architektur,$SHELLIdentifizierung von Bash/zsh/Fish,Sigstore-Mitunterzeichner,tar,uname,install, Standard-Shell-Dienstprogramme, ein SHA-256-Befehl (sha256sum,shasum, odersha256) und einen Downloader (curl,wget, oder Python). Das Beispiel verwendet Curl. FreeBSD benötigt außerdem Bash. Ihr Home-/Installationsverzeichnis muss beschreibbar sein.

Laden Sie die Datei in eine lokale Datei herunter, überprüfen Sie sie mit einem Editor und führen Sie sie nur aus, wenn Sie der Quelle und dem Verhalten vertrauen. Eine Inspektion ist keine Garantie für Sicherheit; Führen Sie diese Schritte nicht blind aus:

curl -fsSL https://jonconradt.github.io/ash/install.sh -o ash-install.sh
less ash-install.sh

Führen Sie die gespeicherte Kopie nach der Überprüfung als Ihr normaler Benutzer aus:

sh ./ash-install.sh
rm ./ash-install.sh

install.shlädt die neueste Version herunter, überprüft das von Sigstore signierte Prüfsummenmanifest und den Archiv-Digest und installiertash/ash-brokerIn~/.local/bin. Native Plugins gehen unter$XDG_DATA_HOME/ash/plugins. Es führt das Setup pro Benutzer aus und fragt nach, bevor die Shell-Integration aktiviert wird. Ohne ein interaktives Terminal können Anbieter-/Integrationsaufforderungen übersprungen werden: Ausführenash installanschließend interaktiv.

Sie können einstellenASH_INSTALL_DIRbevor Sie das Skript ausführen, um ein anderes Ziel auszuwählen. Fügen Sie dieses Ziel selbst zu PATH hinzu.Die Selbstaktualisierung wird nur unter unterstützt~/.local/bin; Benutzerdefinierte Ziele müssen manuell ersetzt werden. Das Skript verfügt über keinen Beta/Nightly-Selektor.

Überprüfen Sie ein direktes Paket oder Archiv

Voraussetzungen: Cosign und ein SHA-256-Dienstprogramm. Laden Sie Ihr Paket/Archiv aus derselben veröffentlichten Version herunter.SHA256SUMS, UndSHA256SUMS.sigstore.json. Arbeiten Sie in einem neuen Verzeichnis. ErsetzenvX.Y.Zmit dem genauen Tag, gegebenenfalls einschließlich eines Vorabversionssuffixes:

cosign verify-blob SHA256SUMS \
  --bundle SHA256SUMS.sigstore.json \
  --certificate-identity "https://github.com/Jonconradt/ash/.github/workflows/release.yml@refs/tags/vX.Y.Z" \
  --certificate-oidc-issuer "https://token.actions.githubusercontent.com"

Erst wenn dies gelingt, berechnen Sie den Digest Ihrer Datei mitshasum -a 256 PACKAGEauf macOS,sha256sum PACKAGEunter Linux, bzwsha256 -q PACKAGEauf FreeBSD. ErsetzenPACKAGEmit dem heruntergeladenen Dateinamen und vergleichen Sie ihn genau mit dem Eintrag dieses Dateinamens im überprüften Manifest. Stoppen Sie bei einem fehlenden Eintrag oder einer Nichtübereinstimmung. Eine neben einer Datei heruntergeladene unsignierte Prüfsumme ist nicht gleichbedeutend mit verifizierten Herausgeber-Metadaten.

Updates und die drei Kanäle

  • Veröffentlichung (empfohlen):stabile veröffentlichte Versionen wievX.Y.Z; Die Repository-Konfiguration ruft dies aufstable.
  • Beta:Tests vor der Veröffentlichung, getaggtvX.Y.Z-beta.N; Erwarten Sie Veränderungen und Rückschritte.
  • Nacht:Letzte Änderungen am Standardzweig, markiertvX.Y.Z-nightly.YYYYMMDD.N; das höchste Regressionsrisiko. Builds sind geplant, können aber übersprungen werden, wenn sich nichts ändert oder die Veröffentlichung fehlschlägt.

Eine veröffentlichte Version aktualisiert die entsprechende Homebrew-Formel oder das signierte Linux-Repository. Sie erhalten es, wenn Sie den Upgrade-Befehl des besitzenden Managers ausführen (oder Ihre eigene Betriebssystem-Update-Richtlinie tut dies). Veröffentlichung, Repository-Aktualisierungen und Website-Bereitstellung können sich gegenseitig verzögern; Überprüfen Sie die Verfügbarkeit, bevor Sie den Sender wechseln. ash installiert keine Hintergrund-Binäraktualisierungen im Hintergrund.

Homebrew: Formeln installieren oder wechseln

Für eine neue Beta-/Nightly-Installation verwenden Sie den entsprechenden vollständigen Formelnamen oben in brew install. Deinstallieren Sie beim Wechsel zunächst die aktuell installierte Formel: Alle drei stellen die gleichen Binärdateien bereit. Beispiel, Release zur Beta:

brew uninstall ash
brew install Jonconradt/ash/ash-beta
brew update
brew upgrade ash-beta

Verwendenash-nightlyfür Nightly oderashfür Release in den Installations-/Upgrade-Befehlen. Deinstallieren Sie die eigentliche Formel des alten Kanals, nicht immerash. Benutzereinstellungen bleiben erhalten; Öffnen Sie nach dem Wechsel eine neue Shell.

Linux: Wählen Sie einen Repository-Kanal aus

GEEIGNET:Benutze dieAPT-Setupmit genau einer Verteilung aus der Tabelle. Um eine bestehende Installation zu ändern, bearbeiten Sie sie/etc/apt/sources.list.d/versionx.list, ersetzenstablemitbetaodernightly(oder zurück zustable), Dann:

sudo apt update
sudo apt install --allow-downgrades ash

DNF:Benutze dieDNF-Setupmit der ausgewählten Basis-URL. Bei einer vorhandenen Installation ersetzenbaseurlIn/etc/yum.repos.d/versionx.repo, wobei die Signatureinstellungen beibehalten werden, dann:

sudo dnf --refresh distro-sync ash

Pacman:Benutze diePacman-Setupmit der ausgewählten Server-URL. Behalten Sie den Abschnittsnamen bei[versionx]: Jeder Kanal veröffentlicht eine Datenbank mit dem Namenversionx.db. Ändern Sie den Server in diesem einen Abschnitt, anstatt eine Datenbank mit einem anderen Namen hinzuzufügen. Um zu wechseln, einschließlich Downgrade:

sudo pacman -Syuu ash

Überprüfen Sie die vorgeschlagene Transaktion: Durch die Rückkehr zu Release kann ash herabgestuft werden, und Pacmans Double u kann auch andere Pakete herabstufen. Sichern Sie die Konfiguration vor dem Wechsel. Verwenden Sie anschließend die normalen APT/DNF/Pacman-Upgrade-Befehle aus den Betriebssystemabschnitten; Lassen Sie nicht mehrere ash-Kanalquellen aktiviert.

Benutzerlokale Release-Updates

ash update

Dadurch wird eine stabile Version nur dann überprüft und installiert, wenn sie aktiv istashDie ausführbare Datei befindet sich unter~/.local/bin. Außerdem werden gebündelte Assets/Plugins aktualisiert, mit Auswahlmöglichkeiten für benutzerdefinierte Dateien.ash update --version vX.Y.Zwählt ein stabiles Tag aus, keinen Kanal; Es handelt sich nicht um einen Downgrade-Befehl. Es gibt keine--channelOption. Paketmanager-Installationen, macOS .pkg-Installationen und benutzerdefinierte Skriptziele müssen stattdessen ihren eigenen Manager/Installer verwenden. FreeBSD Beta/Nightly verwendet manuell überprüfte Archive, kein Selbst-Updater-Abonnement. Öffnen Sie nach dem Update eine neue Shell.

Deinstallieren, ohne nicht verwandte Dateien zu entfernen

1. Deaktivieren Sie zuerst die Shell-Integration.

Bevor Sie Binärdateien entfernen, führen Sie den Befehl für jede Shell aus, in der Sie die Integration aktiviert haben:

Bash

ash install --shell bash --disable-shell-integration

zsh

ash install --shell zsh --disable-shell-integration

Fisch

ash install --shell fish --disable-shell-integration

Wennashfehlt bereits, bearbeiten Sie die entsprechende Startdatei vonInitialisierungund entfernen Sie nur den Block dazwischen# >>> ash install >>>Und# <<< ash install <<<. Entfernen Sie alleash-spezifische PATH-/Umgebungszeilen, die Sie manuell hinzugefügt haben, keine unabhängige Shell-Konfiguration. Schließenash-aktivierte Shells anschließend, sodass ihre Shell-eigenen Broker beendet werden.

2. Lassen Sie den besitzenden Paketmanager seine Dateien entfernen

Homebrew (Veröffentlichung)

brew uninstall ash

APT

sudo apt remove ash

Nicht verfügbar

sudo dnf remove ash

Pacman

sudo pacman -R ash

Wählen Sie nur Ihre Installationsmethode; für Homebrew Beta/nächtliche Nutzungash-beta/ash-nightly. APT/DNF/Pacman entfernt paketeigene Binärdateien, Plugins und Manpages, nicht die Konfiguration/den Verlauf Ihres Home-Verzeichnisses. Löschen Sie paketeigene Dateien nicht manuell.

Optionale Repository-Bereinigung: Entfernen Sie dieashQuelldatei/etc/apt/sources.list.d/versionx.listund es ist gewidmet/etc/apt/keyrings/versionx-keyring.gpg, oder dieashRepository-Datei/etc/yum.repos.d/versionx.repo, oder dieash [versionx]Abschnitt aus/etc/pacman.conf. Überprüfen Sie zunächst, dass keine anderen Pakete sie verwenden. Entfernen Sie einen importierten RPM/Pacman-Vertrauensschlüssel erst, nachdem Sie seinen Fingerabdruck bestätigt haben und sichergestellt haben, dass nichts anderes von ihm abhängt. Löschen Sie niemals den gemeinsamen Schlüsselbund einer Distribution.

3a. Manuelle Entfernung von macOS .pkg

macOS Installer zeichnet eine Quittung auf, hat aber keineashDeinstallationsprogramm. Bestätigen Sie, dass es sich um eine .pkg-Installation und nicht um Homebrew handelt, und überprüfen Sie die genaue Nutzlast:

pkgutil --pkg-info dev.ash.cli
pkgutil --files dev.ash.cli

Verwenden Sie diese Quittung als Inventar und entfernen Sie nur dieseash-eigene Dateien:/usr/local/bin/ash,/usr/local/bin/ash-broker, die Dateien in/usr/local/lib/ash/plugins,/usr/local/share/man/man1/ash.1, die aufgeführten lokalisiertash.1Seiten und Hinweise in/usr/local/share/licenses/ash. Es sind Administratorrechte erforderlich. Überprüfen Sie den Besitz, wenn ein anderer Installer diese Dateien später ersetzt hat; Entfernen Sie nicht die Kopie. Leer entnehmenash-nur Verzeichnisse, nicht freigegeben/usr/local,bin, oder Man-Verzeichnisse.

Nachdem Sie die Nutzlast entfernt haben, entfernen Sie optional die Quittung:

sudo pkgutil --forget dev.ash.cli

Durch das Vergessen einer Quittung werden keine installierten Dateien entfernt.Bewahren Sie es auf, bis Sie die Überprüfung der Nutzlast abgeschlossen haben.

3b. Manuelle Entfernung des benutzerlokalen/Linux/FreeBSD-Archivs

Suchen Sie die aktive Kopie mitcommand -v ashUndcommand -v ash-broker. Entfernen Sie für die Standardskriptinstallation nach dem Deaktivieren der Hooks diese beiden spezifischen Dateien:

rm "$HOME/.local/bin/ash" "$HOME/.local/bin/ash-broker"

FürASH_INSTALL_DIRoder ein manuell extrahiertes Archiv, entfernen Sie nur das tatsächlich installierteash/broker-Pfade. Entfernen Sie Archiv-Plugins/Manpages/Hinweise, die Sie mit Ihrem ursprünglichen Dateibestand installiert haben; Skript-Plugins sind in derashBenutzerdatenverzeichnis. Wenn Dateien unter sind/usr/bin, überprüfen Sie zuerst den Besitz mitdpkg -S /usr/bin/ash,rpm -qf /usr/bin/ash, oderpacman -Qo /usr/bin/ashje nach Bedarf. Eine paketeigene Kopie muss über diesen Manager entfernt werden, auch wenn sie über einen eigenständigen Download installiert wurde.

4. Optional: Lokale Einstellungen, Tools und Verlauf löschen

Sichern Sie alles, was Sie behalten möchten. Dieser separate Schritt kann Anbietereinstellungen/Tokens, benutzerdefinierte Tools/Plugins, Konversationsverlauf und Arbeitsdateien löschen. Das Deinstallieren von Binärdateien bedeutet nicht die Zustimmung zu deren Löschung.

  • Konfiguration:$XDG_CONFIG_HOME/ash, Standard~/.config/ash.
  • Daten, Plugins und Python-Umgebung:$XDG_DATA_HOME/ash, Standard~/.local/share/ash.
  • Geschichte und Zustand:$XDG_STATE_HOME/ash, Standard~/.local/state/ash.
  • Cache:$XDG_CACHE_HOME/ash, Standard~/.cache/ash.
  • Laufzeit des Brokers:$XDG_RUNTIME_DIR/ash, oder$XDG_STATE_HOME/ash/runtimewenn kein Laufzeit-Root verfügbar ist.

Überprüfen Sie Ihre tatsächlichen absoluten XDG-Überschreibungen, bevor Sie nur diese ash-Unterverzeichnisse löschen. Löschen Sie niemals ein XDG-Stammverzeichnis oder Ihr Home-Verzeichnis. Nachdem alle ash-aktivierten Shells geschlossen wurden, entfernen Sie bei Bedarf übrig gebliebene ash-Laufzeitdateien. MCP-OAuth-Anmeldeinformationen können auch im OS-Anmeldeinformationsmanager verbleiben: Entfernen Sie dort ash-spezifische Einträge und entziehen Sie den Zugriff beim MCP-Anbieter. Nicht verwendete AI-Schlüssel in ihren Anbieterkonten widerrufen; Durch das Löschen einer lokalen Datei wird kein Schlüssel widerrufen. Deinstallieren Sie Ollama/models, Python oder gemeinsame Abhängigkeiten nicht als Teil der ash-Entfernung.

Schnelle Fehlerbehebung

Befehl nicht gefunden oder falsche Version
Überprüfen Sie PATH undcommand -v ash/command -v ash-broker. Ein alter~/.local/bincopy kann ein Paket schatten. Verwenden Sie jeweils einen Besitzer/Kanal und öffnen Sie eine neue Shell.
Das Anbietermenü wurde nicht angezeigt
Laufenash installvon einem interaktiven Terminal aus. Vorhandene gültige Einstellungen bleiben erhalten; verwendenmanuelle Konfigurationden Anbieter zu wechseln. Stellen Sie ohne Integration sicher, dass die Einstellungen in die CLI-Umgebung exportiert werden.
Kein Modell oder Anschluss abgelehnt
Bestätigen Sie für Ollama, dass der Server ausgeführt wirdollama listbeinhaltet das von Ihnen gewählte Modell. Überprüfen Sie bei Cloud-Diensten Endpunkt, Modellberechtigung, HTTPS, Token und Kontokontingent. Geben Sie niemals tokentragende Protokolle weiter.
Repository oder Kanal nicht verfügbar
Überprüfen Sie die Architektur und das veröffentlichte Release/Repository. Die Veröffentlichung kann verzögert erfolgen; Deaktivieren Sie die Signaturüberprüfung nicht, um ein nicht verfügbares Repository zu umgehen.
Die Einrichtung des Python-Tools ist fehlgeschlagen
Installieren Sie Python mit venv/ensurepip und lassen Sie Abhängigkeitsdownloads zu. Führen Sie es dann erneut ausash install. Basicashbleibt auch ohne diese Werkzeuge nutzbar.
