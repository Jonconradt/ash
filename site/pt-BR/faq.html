Primeiros passos

O que preciso antes de poder usar ash?

Você precisa do executável ash, de um endpoint de IA e de um nome de modelo. A execução de ash install configura-os automaticamente: ele usa uma chave de API do provedor de nuvem já definida ou um servidor de inferência local em execução quando encontrado; caso contrário, mostra um menu de provedor numerado e solicita uma chave de API e, em seguida, permite escolher um modelo na lista de modelos do terminal. Você também pode definir AI_ENDPOINT e AI_MODEL manualmente. Um endpoint local como Ollama pode usar http://localhost:11434, e um host LAN como http://brain.local:11434 ou um IP privado também é tratado como local (a menos que ASH_STRICT=1); Os terminais em nuvem devem usar HTTPS e também exigir AI_AUTH_TOKEN. A integração do shell é opcional: você sempre pode executar ash "your question" diretamente.

Onde o ash é instalado e como verifico se meu shell pode encontrá-lo?

O instalador verificado coloca ash em ~/.local/bin/ash e ash install adiciona esse diretório ao seu PATH por meio do arquivo gerenciado ~/.ash/.ash_env. Abra um novo terminal e execute command -v ash para confirmar. O atualizador automático instala seu binário substituto no mesmo local ~/.local/bin/ash.

Como faço para usar ash sem alterar meu shell?

Passe diretamente um prompt entre aspas: ash "how do I find large files?". Sem argumentos, ash também aceita um prompt de entrada padrão não interativo, como git diff | ash. O uso direto é a opção menos surpreendente quando você está aprendendo ash ou escrevendo um script.

Por que ash diz que minha configuração de IA está incompleta?

Verifique se AI_ENDPOINT e AI_MODEL não estão vazios no ambiente onde ash é executado. Para um nome de host de nuvem, defina também AI_AUTH_TOKEN. Execute printf '%s\n' "$AI_ENDPOINT" "$AI_MODEL" para confirmar se os dois primeiros valores estão presentes, mas não imprima um token de autenticação em uma gravação de terminal ou log compartilhado.

Instalação e atualização

ash funciona no Windows 11?

Não nativamente. ash suporta bash, zsh e Fish no macOS, Linux e FreeBSD; não há destino de instalação do PowerShell. Use WSL para a experiência Linux compatível.

Como faço para instalar ash no subsistema Windows para Linux (WSL)?

Instale-o dentro de sua distribuição WSL como Linux: curl -fsSL https://jonconradt.github.io/ash/install.sh | sh. Em seguida, configure AI_ENDPOINT e AI_MODEL e execute ash install para o shell em execução no WSL.

Como atualizo ash para a versão de lançamento mais recente?

Execute ash update no macOS, Linux ou FreeBSD. Ele baixa o arquivo correspondente estável mais recente, verifica o manifesto de lançamento com seu pacote Sigstore e resumo SHA-256 e, em seguida, instala em ~/.local/bin/ash. Se a verificação da assinatura falhar ou o arquivo contiver entradas não suportadas, será necessária uma confirmação interativa; não aprove uma assinatura com falha, a menos que você confie de forma independente na fonte de liberação. Cargas não suportadas são ignoradas e execuções não interativas recusam essas exceções. Use ash update --version vX.Y.Z para uma versão específica; use --yes somente quando quiser substituir arquivos gerenciados personalizados.

Executei ash install. Por que nada muda neste terminal?

A instalação atualiza um arquivo de inicialização; ele não reescreve o processo shell já em execução. Abra um novo terminal ou recarregue o arquivo para seu shell: source ~/.bashrc para Bash, source ~/.zshrc para zsh ou source ~/.config/fish/config.fish para Fish, a menos que você use um XDG_CONFIG_HOME personalizado.

Comandos desconhecidos ainda dizem “não encontrado”. Como soluciono problemas de integração do shell?

Primeiro execute command -v ash; o wrapper não pode invocar um binário que seu shell não consegue encontrar. Em seguida, recarregue ou reinicie o shell e verifique se seu arquivo de inicialização contém o bloco gerenciado >>> ash install >>>. Por fim, execute ash snooze off, porque uma soneca deixa intencionalmente comandos desconhecidos como falhas normais “não encontradas”.

Quais arquivos o ash install altera e posso visualizá-lo?

Ele adiciona ou atualiza um bloco marcado ash no arquivo de inicialização do shell selecionado e gerencia arquivos em ~/.ash, incluindo configuração, wrappers e pacotes ferramentas. Execute ash install --shell bash --dry-run para visualizar a alteração do arquivo de inicialização sem gravá-la. A nova execução da instalação é idempotente; use --overwrite somente quando desejar que os arquivos de bootstrap gerenciados sejam atualizados.

ash suporta Fish?

Sim. Execute ash install --shell fish. ash adiciona um bloco gerenciado a $XDG_CONFIG_HOME/fish/config.fish ou ~/.config/fish/config.fish quando XDG_CONFIG_HOME não está definido. Fish usa fish_command_not_found, então um comando não resolvido alcança ash com seus argumentos originais.

Por que não test e type minúsculos em Fish?

Fish reserva esses nomes minúsculos como componentes essenciais e não permite que uma função os substitua. Use Test ... ou Type ... para expressar a intenção ash ou invoque ash "..." diretamente. Outros wrappers de colisão compatíveis permanecem disponíveis.

E quanto ao ksh93?

ksh93 não é suportado para integração de shell. Seu comportamento FPATH só pode carregar um arquivo com o nome de um comando desconhecido; ele não possui retorno de chamada genérico de comando não encontrado que possa implementar com segurança o roteamento de prompt ash ou o ciclo de vida do corretor.

IA e conexões

ash inclui a IA?

Não. ash é um cliente para um terminal de IA que você configura. Definir AI_ENDPOINT e AI_MODEL; ash suporta Ollama local e outros servidores locais compatíveis com OpenAI (LM Studio, llama.cpp, MLX, LocalAI, vLLM, text-generation-webui, Jan, GPT4All) e detecta adaptadores de provedor de nuvem compatíveis a partir do endpoint, com uma substituição AI_PROVIDER opcional.

O que são servidores MCP e como adiciono one?

Os servidores MCP (Model Context Protocol) expõem ferramentas que um modelo de IA pode chamar, como pesquisa, análise ou ações específicas de serviço. Para adicionar um servidor Streamable HTTP MCP remoto, coloque seu URL em sua própria linha em ~/.ash/.ash_allow e execute ash novamente. Por exemplo: https://mcpplaygroundonline.com/mcp-complex-server. Ash se conecta através de seu corretor e oferece as ferramentas do servidor ao modelo. Use apenas servidores em que você confia: suas ferramentas podem realizar ações em seu nome. HTTPS é necessário, exceto para servidores de desenvolvimento localhost. Os arquivos ~/.ash/mcp.json existentes não são mais lidos; mova seus URLs para .ash_allow. Se a inicialização do MCP falhar, ash continua sem ferramentas MCP remotas: ele avisa em sessões interativas e permanece silencioso em sessões não interativas.

Os trabalhos agendados podem usar servidores MCP?

Não. Os trabalhos agendados e outros trabalhos não interativos não herdam um intermediário do shell interativo, portanto, as ferramentas MCP remotas não estão disponíveis. Ash ainda executa o prompt sem ferramentas MCP e suprime essa falha de inicialização esperada. Um prompt que depende do MCP pode, portanto, terminar sem os dados ou ações solicitadas. Não agende prompts que exijam MCP.

O MCP funciona quando ASH_STRICT=1?

Sim. Uma linha de URL HTTP(S) registra explicitamente um servidor MCP e não é tratada como um executável de shell. O modo estrito não desativa os servidores MCP configurados. Ele ainda aplica as proteções de saída não confiável de Ash ao conteúdo da ferramenta retornado.

Como funciona o MCP OAuth e onde as credenciais são armazenadas?

Para um servidor protegido por OAuth, Ash abre a página de autorização no navegador do desktop quando uma GUI está disponível; se não conseguir abrir um navegador, ele imprime uma URL para autorizar manualmente em um navegador no mesmo host. Use ash mcp add <url> --no-browser para sempre usar o fluxo do terminal. Para conexões OAuth diretas, a descoberta permite endereços IP não públicos apenas para a autoridade MCP registrada exata; outros hosts OAuth permanecem sujeitos ao bloqueio de endereços não públicos. Um proxy de saída configurado é responsável por filtrar seus endereços de destino. O corretor lida com o retorno de chamada, troca de token, atualização e sessão MCP persistente. As credenciais são armazenadas no gerenciador de credenciais do sistema operacional, quando disponíveis. Se não estiver disponível, configure o substituto do arquivo criptografado usando um ASH_MCP_CREDENTIAL_KEY aleatório de 32 bytes; Ash nunca armazena a chave em si.

Onde posso encontrar o AUTH_KEY para os provedores de IA em nuvem mais populares?

ash chama esse valor de AI_AUTH_TOKEN; ele não cria nem distribui chaves de provedor. Crie uma chave na conta do seu provedor, como OpenAI, Anthropic, Google AI Studio, Azure OpenAI, Mistral, Cohere, Groq, xAI, DeepSeek, Together AI, OpenRouter, HuggingFace ou Ollama e exporte-o como a variável de ambiente do provedor (ou AI_AUTH_TOKEN diretamente). ash install detecta automaticamente a maioria dessas variáveis ​​de ambiente específicas do provedor. Os endpoints de nuvem devem usar HTTPS e exigir um token; Endereços privados/LAN e nomes de host .local não são tratados como terminais de nuvem, a menos que ASH_STRICT=1 seja definido.

ash abre uma nova conexão a cada vez?

Não é para uso normal do shell Unix interativo. Bash, zsh e Fish iniciam um broker por sessão de shell, comunicam-se com ele por meio de um soquete Unix privado e reutilizam seu pool de conexões HTTP limitado. O corretor sai após inatividade; trabalhos agendados usam solicitações diretas em vez de um intermediário de shell persistente.

O Fish usa o corretor?

Sim. O wrapper Fish inicia e reutiliza o mesmo broker por sessão que bash e zsh, atualiza seu arrendamento imediatamente antes de uma solicitação ash e mantém a configuração do broker silenciosa.

O que acontece se uma solicitação for lenta, indisponível ou eu mudar de ideia?

Pressione Ctrl-C para cancelar uma solicitação em andamento. O tempo limite padrão da solicitação de IA é de três minutos; defina AI_TIMEOUT, por exemplo AI_TIMEOUT=90s, para alterá-lo. ash tenta novamente falhas de IA repetíveis até três vezes por padrão com uma espera curta e limitada; ajuste esse comportamento com ASH_RETRY_MAX_ATTEMPTS, ASH_RETRY_BASE_DELAY e ASH_RETRY_MAX_DELAY.

Segurança e controle

Como faço para bloquear ash para ser mais seguro e quais são as implicações?

Mantenha a lista de permissões executáveis ​​restrita, dê preferência a ferramentas somente leitura e não adicione comandos privilegiados ou destrutivos. Defina ASH_STRICT=1 para bloquear padrões de injeção de prompt reconhecidos de ferramentas, arquivos, scripts, pipelines e saídas de agentes filhos não confiáveis. Isso também pode ocultar texto legítimo que se assemelha a uma tentativa de injeção. A lista de permissões é um limite de execução, não uma sandbox: ash e as ferramentas permitidas ainda são executadas como você.

O ash pode executar comandos destrutivos como rm?

Não com a lista de permissões padrão instalada. Ele desaconselha explicitamente rm, mv, dd, chmod, chown, kill e sudo. Se você adicionar um deles, ash poderá solicitá-lo com suas permissões; revise essa decisão com cuidado.

Como altero os comandos que ash pode executar?

Edite ~/.ash/.ash_allow e liste os nomes simples dos executáveis, um por linha ou separados por vírgula. Suas diretivas autônomas $TOOLS_DIR_LIST e $PLUGINS_DIR_LIST permitem scripts gerenciados e plug-ins nativos elegíveis; substitua-os por nomes literais para uma política restritiva. Scripts e plug-ins elegíveis são arquivos regulares em ~/.ash/tools/ ou ~/.ash/plugins/ com bits de leitura e execução. Você também pode negar comandos explicitamente adicionando-os a ~/.ash/.ash_deny. Alternativamente, configure ASH_ALLOW ou ASH_DENY para uma lista separada por vírgulas. As alterações são lidas na próxima solicitação ash.

Em qual usuário ash está sendo executado?

ash e todas as ferramentas permitidas são executadas como o usuário que inicia ash. Não eleva privilégios. O espaço de trabalho gerenciado ~/.ash tem permissão reforçada, mas seu conteúdo permanece acessível ao usuário e a qualquer processo que você permitir explicitamente.

O ash confia no texto recebido via canal da mesma forma que no texto do usuário? Quais proteções existem para dados maliciosos?

Sim. Quando ash não recebe argumentos de linha de comando e a entrada padrão é canalizada, ele trata essa entrada como o prompt do usuário. Não canalize páginas da web, logs ou texto gerado não confiáveis ​​diretamente para ash, a menos que você pretenda autorizá-lo como um prompt. Isso difere da ferramenta gerenciada por ash, arquivo, script, pipeline e saída do agente filho: ash rotula esses resultados como evidências não confiáveis ​​e instrui o modelo a nunca seguir as instruções deles. Defina ASH_STRICT=1 para substituir adicionalmente frases de injeção imediata reconhecidas em evidências não confiáveis. As regras de execução da lista de permissões e do argumento direto ainda se aplicam à execução da ferramenta.

Meus arquivos ash são privados de outros usuários neste computador?

Durante a instalação, ash protege o diretório ~/.ash para permissões somente do proprietário e os arquivos gerenciados para permissões legíveis e graváveis ​​pelo proprietário. Isso protege contra outras contas locais com permissões normais do Unix, mas não contra sua própria conta, administradores, backups ou software que você escolhe executar com acesso ao seu diretório inicial.

Ferramentas e fluxo de trabalho

ash suporta pipes e outras tradições Unix?

Sim. Você pode canalizar texto para ash como um prompt, por exemplo git diff | ash. Para pipelines de ferramentas solicitados por IA, ash oferece suporte de dois a dezesseis executáveis ​​na lista de permissões conectados diretamente sem um shell, como ls | grep pattern | pbcopy. Os padrões de controle de shell nos argumentos da ferramenta são bloqueados, e todos os executáveis ​​em um pipeline gerenciado por ash devem ser incluídos na lista de permissões.

O ash reinterpretará comandos dentro de meus scripts de shell, comandos SSH ou tarefas cron?

Não. Os wrappers de integração Bash e zsh retornam imediatamente em shells não interativos, portanto, scripts, trabalhos de CI, linhas únicas SSH e comandos cron mantêm o comportamento normal de comando não encontrado. Use uma invocação explícita como ash "summarize this log" ou some-command | ash quando a automação precisar chamar ash.

Como faço para impedir que ash interprete meus comandos por alguns minutos?

Execute ash snooze pelos cinco minutos padrão ou especifique uma duração como ash snooze 30s ou ash snooze 1h. Execute ash snooze off para retomar imediatamente. A soneca pausa o roteamento automático de comandos não encontrados e de wrapper; comandos explícitos ash ... ainda funcionam.

Como posso depurar ash e ver mais informações sobre o que ele está fazendo?

Defina ASH_VERBOSE=1 antes de executar ash para ativar a saída de depuração estruturada e um painel de execução de terminal. Defina ASH_LOG_FILE para gravar JSON de depuração em um arquivo; ASH_LOG_MAX_BYTES controla a rotação e o padrão é 1 MiB quando um arquivo de log é configurado.

Quais limites se aplicam quando ash executa ferramentas?

Por padrão, cada chamada de ferramenta tem um tempo limite de 15 segundos e captura até 8.192 bytes de saída. Uma solicitação de IA pode fazer até 16 iterações de loop de ferramentas, e um pipeline gerenciado por ash tem de dois a dezesseis estágios. Ajuste o tempo limite da ferramenta e o limite de saída com ASH_TOOL_TIMEOUT e ASH_TOOL_OUTPUT_MAX; mantenha o foco da saída com comandos como head, tail ou grep.

Onde está o prompt padrão do sistema?

O arquivo de prompt canônico é ~/.ash/.ash_system, instalado a partir do pacote padrão quando você executa ash install. ash lê esse arquivo primeiro. Se estiver ausente, ash volta para .ash_system no diretório de trabalho atual e depois para ~/.ash_system. Os valores comuns $VARIABLE são expandidos do ambiente, mas $TOOLS_DIR_LIST, $PLUGINS_DIR_LIST e $IF_PYTHON_AVAILABLE são substituições internas reservadas Ash e nunca derivadas do ambiente.

Onde coloco meus próprios scripts e plug-ins nativos para ash chamar como ferramentas?

Coloque scripts Python em ~/.ash/tools/ e plug-ins binários nativos compilados em ~/.ash/plugins/. Certifique-se de que sejam executáveis ​​e adicione o nome do executável simples a ~/.ash/.ash_allow (ou confie em $TOOLS_DIR_LIST / $PLUGINS_DIR_LIST). ash não invoca um shell para comandos e plug-ins Unix permitidos.

Quais são as práticas recomendadas para uma ferramenta ou plug-in para que a IA entenda sua finalidade e uso?

Siga o padrão de ferramenta/plug-in padrão: exponha opções previsíveis com argumentos CLI; e implementar uma opção --ai-docs que explica os recursos, cada argumento e padrão, esquema de saída, estados de falha e quando a IA deve usar a ferramenta. Emita JSON estruturado compacto com um campo status e detalhes de erro acionáveis ​​em vez de prosa misturada com dados. Mantenha a saída limitada, valide entradas, defina tempos limite de rede, lide com falhas esperadas e torne a ferramenta segura para chamadas repetidas. Adicione seu nome de arquivo simples a ~/.ash/.ash_allow; ash pode executá-lo somente quando estiver na lista de permissões e não estiver listado em ~/.ash/.ash_deny.

Quais são os scripts de ferramentas e plug-ins nativos fornecidos?

Os scripts Python de bootstrap instalados são headlines.py, wikipedia.py e yfinance.py em ~/.ash/tools/. Os plug-ins nativos fornecidos são what_time_is_it (Go), flip_a_coin (Rust) e calculator (TypeScript) em ~/.ash/plugins/.

ash pode chamar subagentes?

Sim. Um agente pai pode usar run_sub_agent para uma tarefa independente e focada. Um filho herda o diretório de trabalho, a configuração, as ferramentas e as permissões do sistema operacional, retorna um resultado limitado e não pode criar outro filho. O máximo padrão é de seis subagentes por execução pai e pode ser alterado com ASH_MAX_AGENTS.

O ash pode gerar arquivos de memória para rastrear tarefas complexas e o que aprendeu na sessão?

Sim. Ele pode gravar arquivos de espaço de trabalho persistentes em ~/.ash, que são rastreados em ~/.ash/inventory.md, e arquivos temporários com escopo de sessão em ~/.ash/scratch/<session-id>/. Use arquivos de espaço de trabalho persistentes para informações que você pretende manter; use arquivos de rascunho para planos temporários, notas e artefatos auxiliares.

ash pode agendar trabalhos para mais tarde?

Sim, por meio de suas ferramentas de IA. No macOS, o agendamento único usa um LaunchAgent por usuário launchd e requer launchctl. No Linux, os agendamentos recorrentes são suportados através do seu usuário crontab; ash gerencia apenas suas próprias entradas marcadas. O planejador único launchd não está disponível no Linux, portanto, use uma entrada cron ou outro planejador do Linux para uma tarefa única do Linux. As execuções agendadas recebem um ambiente limitado e usam HTTPS direto em vez de um agente de shell interativo, portanto, certifique-se de que a configuração de IA necessária esteja disponível para o trabalho agendado. Eles não podem usar ferramentas MCP remotas; Ash é executado sem eles e não avisa em sessões não interativas. Não agende prompts que exijam MCP.

Sessões e armazenamento

Onde estão o histórico ou os arquivos de log de ash?

O histórico de conversas é armazenado como JSON em ~/.ash/history/<SESSION_ID>.json; execuções programadas usam task_<SESSION_ID>.json. Quando o log de depuração agendado está ativado, seu local de log padrão é ~/.ash/logs/task_<SESSION_ID>.log. Você pode escolher outro caminho de log de depuração com ASH_LOG_FILE.

Por quanto tempo os arquivos de histórico são retidos?

ash remove arquivos JSON de histórico com mais de 14 dias durante a limpeza normal do aplicativo, com um orçamento de limpeza de 300 ms para que a saída não seja atrasada. A janela de mensagens recentes é separada: ela mantém até 40 mensagens por conversa por padrão e pode ser alterada com ASH_HISTORY_MAX.

Como faço para limpar uma conversa ou começar do zero?

O histórico é separado por ID de sessão e endpoint/chave de modelo de IA. Inicie uma nova sessão de terminal para um novo ID de sessão ou remova o arquivo JSON relevante em ~/.ash/history/ quando desejar descartar intencionalmente esse histórico de conversa local. A remoção de um arquivo de histórico não revoga uma chave do provedor nem exclui dados do lado do provedor; gerencie-os separadamente com o provedor.

O que é SESSION_ID e onde ele é gerado?

É o identificador por sessão usado para separar histórico, espaço de trabalho, soquetes de corretor e nomes de log agendados. O ambiente shell gerenciado gera um valor alfanumérico aleatório de 16 caracteres de /dev/urandom quando o shell é iniciado; ash também cria um quando uma chamada interativa não tem valor.

Posso substituir a implementação do gerador SESSION_ID?

Você pode fornecer seu próprio SESSION_ID antes de iniciar ash ou personalizar seu arquivo de ambiente gerenciado local, mas ash o valida. Os IDs válidos têm no máximo 128 caracteres e usam letras, dígitos, sublinhados, hifens, com um sufixo de ponto opcional para sessão filha. Não use valores não confiáveis ​​ou compartilhados: as colisões combinam o histórico da sessão e o estado do tempo de execução.

Suporte e comunidade

Como faço para registrar um bug?

Abra um problema em github.com/Jonconradt/ash/issues com a versão ou commit ash, seu sistema operacional e shell, a configuração relevante para o problema com segredos removidos, etapas reproduzíveis e o observado resultado. Para uma vulnerabilidade de segurança, não abra um problema público; relate-o em particular por e-mail ou aviso de segurança do GitHub.

Existe um fórum de discussão no projeto ash?

Sim. Use Discussões do GitHub para perguntas e ideias, e Problemas do GitHub para bugs reproduzíveis e trabalho monitorado.
