Primeros pasos

¿Qué necesito antes de poder usar ash?

Necesita el ejecutable ash, un punto final de IA y un nombre de modelo. La ejecución de ash install los configura automáticamente: utiliza una clave API de proveedor de nube ya configurada o un servidor de inferencia local en ejecución cuando se encuentra; de lo contrario, muestra un menú de proveedor numerado y solicita una clave API, luego le permite elegir un modelo de la lista de modelos del punto final. También puede configurar AI_ENDPOINT y AI_MODEL manualmente. Un punto final local como Ollama puede usar http://localhost:11434, y un host LAN como http://brain.local:11434 o una IP privada también se trata como local (a menos que ASH_STRICT=1); los puntos finales en la nube deben usar HTTPS y también requieren AI_AUTH_TOKEN. La integración de Shell es opcional: siempre puede ejecutar ash "your question" directamente.

¿Dónde se instala ash y cómo compruebo que mi shell pueda encontrarlo?

El instalador verificado coloca ash en ~/.local/bin/ash y ash install agrega ese directorio a su PATH a través del archivo ~/.ash/.ash_env administrado. Abra una nueva terminal, luego ejecute command -v ash para confirmar. El actualizador automático instala su binario de reemplazo en la misma ubicación ~/.local/bin/ash.

¿Cómo uso ash sin cambiar mi shell?

Pase un mensaje entre comillas directamente: ash "how do I find large files?". Sin argumentos, ash también acepta un mensaje de entrada estándar no interactivo, como git diff | ash. El uso directo es la opción menos sorprendente cuando estás aprendiendo ash o escribiendo un script.

¿Por qué ash dice que mi configuración de IA está incompleta?

Comprueba que AI_ENDPOINT y AI_MODEL no estén vacíos en el entorno donde se ejecuta ash. Para un nombre de host en la nube, configure también AI_AUTH_TOKEN. Ejecute printf '%s\n' "$AI_ENDPOINT" "$AI_MODEL" para confirmar que los dos primeros valores están presentes, pero no imprima un token de autenticación en una grabación de terminal o registro compartido.

Instalación y actualización

¿Funciona ash en Windows 11?

No de forma nativa. ash admite bash, zsh y Fish en macOS, Linux y FreeBSD; no hay ningún destino de instalación de PowerShell. Utilice WSL para disfrutar de la experiencia Linux compatible.

¿Cómo instalo ash en el subsistema de Windows para Linux (WSL)?

Instálelo dentro de su distribución WSL como Linux: curl -fsSL https://jonconradt.github.io/ash/install.sh | sh. Luego configure AI_ENDPOINT y AI_MODEL, y ejecute ash install para el shell que se ejecuta dentro de WSL.

¿Cómo actualizo ash a la última versión?

Ejecute ash update en macOS, Linux o FreeBSD. Descarga el archivo de coincidencia estable más reciente, verifica el manifiesto de lanzamiento con su paquete Sigstore y el resumen SHA-256, luego lo instala en ~/.local/bin/ash. Si la verificación de la firma falla o el archivo contiene entradas no compatibles, se requiere una confirmación interactiva; no apruebe una firma fallida a menos que confíe de forma independiente en la fuente de publicación. Las cargas útiles no admitidas se omiten y las ejecuciones no interactivas rechazan estas excepciones. Utilice ash update --version vX.Y.Z para una versión específica; use --yes solo cuando desee reemplazar archivos administrados personalizados.

Ejecuté ash install. ¿Por qué no cambia nada en este terminal?

La instalación actualiza un archivo de inicio; no reescribe el proceso de shell que ya se está ejecutando. Abra una nueva terminal o vuelva a cargar el archivo de su shell: source ~/.bashrc para Bash, source ~/.zshrc para zsh o source ~/.config/fish/config.fish para Fish, a menos que use un XDG_CONFIG_HOME personalizado.

Los comandos desconocidos todavía dicen "no encontrado". ¿Cómo soluciono problemas de integración de shell?

Primero ejecute command -v ash; el contenedor no puede invocar un binario que su shell no puede encontrar. Luego vuelva a cargar o reinicie el shell y verifique que su archivo de inicio contenga el bloque administrado >>> ash install >>>. Finalmente ejecute ash snooze off, porque una repetición deja intencionalmente comandos desconocidos como fallas normales "no encontradas".

¿Qué archivos cambia ash install? ¿Puedo obtener una vista previa?

Agrega o actualiza un bloque marcado ash en el archivo de inicio de shell seleccionado y administra archivos en ~/.ash, incluidos configuración, contenedores y herramientas incluidas. Ejecute ash install --shell bash --dry-run para obtener una vista previa del cambio del archivo de inicio sin escribirlo. Volver a ejecutar la instalación es idempotente; use --overwrite solo cuando desee actualizar los archivos de arranque administrados.

¿ash es compatible con Fish?

Sí. Ejecute ash install --shell fish. ash agrega un bloque administrado a $XDG_CONFIG_HOME/fish/config.fish, o ~/.config/fish/config.fish cuando XDG_CONFIG_HOME no está configurado. Fish usa fish_command_not_found, por lo que un comando no resuelto llega a ash con sus argumentos originales.

¿Por qué no test y type en minúsculas en Fish?

Fish reserva esos nombres en minúsculas como elementos integrados esenciales y no permite que una función los reemplace. Utilice Test ... o Type ... para expresar la intención de ash o invocar ash "..." directamente. Otros contenedores de colisión compatibles siguen estando disponibles.

¿Qué pasa con ksh93?

ksh93 no es compatible con la integración de shell. Su comportamiento FPATH sólo puede cargar un archivo con el nombre de un comando desconocido; no tiene una devolución de llamada genérica de comando no encontrado que pueda implementar de forma segura ash enrutamiento rápido o ciclo de vida del corredor.

IA y conexiones

¿ash incluye la IA?

No. ash es un cliente para un punto final de IA que usted configura. Establezca AI_ENDPOINT y AI_MODEL; ash admite Ollama local y otros servidores locales compatibles con OpenAI (LM Studio, llama.cpp, MLX, LocalAI, vLLM, text-spawn-webui, Jan, GPT4All) y detecta adaptadores de proveedores de nube compatibles desde el punto final, con una anulación AI_PROVIDER opcional.

¿Qué son los servidores MCP y cómo los agrego? ¿uno?

Los servidores MCP (Protocolo de contexto de modelo) exponen herramientas a las que un modelo de IA puede llamar, como búsqueda, análisis o acciones específicas de servicio. Para agregar un servidor MCP HTTP Streamable remoto, coloque su URL en su propia línea en ~/.ash/.ash_allow, luego ejecute ash nuevamente. Por ejemplo: https://mcpplaygroundonline.com/mcp-complex-server. Ash se conecta a través de su broker y ofrece las herramientas del servidor al modelo. Utilice únicamente servidores en los que confíe: sus herramientas pueden realizar acciones en su nombre. Se requiere HTTPS excepto para los servidores de desarrollo localhost. Los archivos ~/.ash/mcp.json existentes ya no se leen; mueva sus URL a .ash_allow. Si la inicialización de MCP falla, ash continúa sin herramientas MCP remotas: advierte en sesiones interactivas y permanece en silencio en sesiones no interactivas.

¿Pueden los trabajos programados usar servidores MCP?

No. Los trabajos programados y otros trabajos no interactivos no heredan el intermediario de un shell interactivo, por lo que las herramientas MCP remotas no están disponibles. Ash aún ejecuta el mensaje sin herramientas MCP y suprime este error de inicialización esperado. Por lo tanto, un mensaje que se basa en MCP puede finalizar sin los datos o la acción solicitada. No programe mensajes que requieran MCP.

¿Funciona MCP cuando ASH_STRICT=1?

Sí. Una línea URL HTTP(S) registra explícitamente un servidor MCP y no se trata como un ejecutable de shell. El modo estricto no deshabilita los servidores MCP configurados. Todavía aplica las protecciones de salida no confiable de Ash al contenido de la herramienta devuelta.

¿Cómo funciona MCP OAuth y dónde se almacenan las credenciales?

Para un servidor protegido con OAuth, Ash abre la página de autorización en el navegador de escritorio cuando hay una GUI disponible; si no puede abrir un navegador, imprime una URL para autorizar manualmente en un navegador en el mismo host. Utilice ash mcp add <url> --no-browser para utilizar siempre el flujo terminal. Para conexiones OAuth directas, el descubrimiento permite direcciones IP no públicas solo para la autoridad MCP registrada exacta; otros hosts de OAuth siguen sujetos al bloqueo de direcciones no públicas. Un proxy de salida configurado es responsable de filtrar sus direcciones de destino. El corredor maneja la devolución de llamada, el intercambio de tokens, la actualización y la sesión MCP persistente. Las credenciales se almacenan en el administrador de credenciales del sistema operativo cuando están disponibles. Si no está disponible, configure el respaldo del archivo cifrado usando un ASH_MCP_CREDENTIAL_KEY aleatorio de 32 bytes; Ash nunca almacena la clave en sí.

¿Dónde puedo encontrar AUTH_KEY para los proveedores de IA en la nube más populares?

ash llama a este valor AI_AUTH_TOKEN; no crea ni distribuye claves de proveedor. Cree una clave en su cuenta de proveedor, como OpenAI, Anthropic, Google AI Studio, Azure OpenAI, Mistral, Cohere, Groq, xAI, DeepSeek, Together AI, OpenRouter, HuggingFace o Ollama, luego expórtelo como la variable de entorno del proveedor (o AI_AUTH_TOKEN directamente). ash install detecta automáticamente la mayoría de estas variables de entorno específicas del proveedor. Los puntos finales de la nube deben usar HTTPS y requerir un token; Las direcciones privadas/LAN y los nombres de host .local no se tratan como puntos finales de la nube a menos que se configure ASH_STRICT=1.

¿ash abre una nueva conexión cada vez?

No es para el uso normal interactivo del shell Unix. Bash, zsh y Fish inician un intermediario por sesión de shell, se comunican con él a través de un socket Unix privado y reutilizan su grupo de conexiones HTTP limitado. El corredor sale después de la inactividad; los trabajos programados utilizan solicitudes directas en lugar de un intermediario de shell persistente.

¿Fish utiliza el intermediario?

Sí. El contenedor Fish inicia y reutiliza el mismo agente por sesión que bash y zsh, actualiza su concesión inmediatamente antes de una solicitud ash y mantiene la configuración del agente en silencio.

¿Qué sucede si una solicitud es lenta, no está disponible o cambio de opinión?

Presione Ctrl-C para cancelar una solicitud en curso. El tiempo de espera predeterminado para la solicitud de IA es de tres minutos; establezca AI_TIMEOUT, por ejemplo AI_TIMEOUT=90s, para cambiarlo. ash reintenta fallos de IA reintentables hasta tres veces de forma predeterminada con un breve retroceso limitado; ajuste ese comportamiento con ASH_RETRY_MAX_ATTEMPTS, ASH_RETRY_BASE_DELAY y ASH_RETRY_MAX_DELAY.

Seguridad y control

¿Cómo bloqueo ash para estar más seguro y cuáles son las implicaciones?

Mantenga la lista de ejecutables permitidos limitada, favorezca las herramientas de solo lectura y no agregue comandos privilegiados o destructivos. Configure ASH_STRICT=1 para bloquear patrones de inyección rápida reconocidos de salidas de herramientas, archivos, secuencias de comandos, canalizaciones y agentes secundarios que no sean de confianza. Esto también puede ocultar texto legítimo que se parezca a un intento de inyección. La lista de permitidos es un límite de ejecución, no un entorno de pruebas: ash y las herramientas permitidas aún se ejecutan como usted.

¿Puede ash ejecutar comandos destructivos como rm?

No con la lista de permitidos predeterminada instalada. Desaconseja explícitamente rm, mv, dd, chmod, chown, kill y sudo. Si agrega uno de ellos, ash puede solicitarlo con sus permisos; revise esa decisión cuidadosamente.

¿Cómo cambio los comandos que ash puede ejecutar?

Edite ~/.ash/.ash_allow y enumere los nombres de los ejecutables básicos, uno por línea o separados por comas. Sus directivas independientes $TOOLS_DIR_LIST y $PLUGINS_DIR_LIST permiten scripts administrados y complementos nativos elegibles; reemplácelos con nombres literales para una política restrictiva. Los scripts y complementos elegibles son archivos normales en ~/.ash/tools/ o ~/.ash/plugins/ con bits de lectura y ejecución. También puede denegar comandos explícitamente agregándolos a ~/.ash/.ash_deny. Alternativamente, establezca ASH_ALLOW o ASH_DENY en una lista separada por comas. Los cambios se leen en la siguiente solicitud ash.

¿Con qué usuario se está ejecutando ash?

ash y cada herramienta permitida se ejecuta como el usuario que inicia ash. No eleva privilegios. El espacio de trabajo ~/.ash administrado tiene permisos reforzados, pero su contenido permanece accesible para su usuario y para cualquier proceso que usted permita explícitamente.

¿Confía ash en el texto recibido a través de la canalización de la misma manera que en el texto del usuario? ¿Qué protecciones existen para los datos maliciosos?

Sí. Cuando ash no recibe argumentos de línea de comando y la entrada estándar se canaliza, trata esa entrada como el mensaje del usuario. No canalice páginas web, registros o texto generado que no sean de confianza directamente a ash a menos que tenga la intención de autorizarlo como un mensaje. Esto difiere de la herramienta, el archivo, el script, la canalización y la salida del agente secundario administrados por ash: ash etiqueta esos resultados como evidencia no confiable e indica al modelo que nunca siga sus instrucciones. Configure ASH_STRICT=1 para reemplazar adicionalmente frases de inyección rápida reconocidas en pruebas que no sean confiables. Las reglas de ejecución de la lista de permitidos y direct-argv aún se aplican a la ejecución de la herramienta.

¿Mis archivos ash son privados de otros usuarios en esta computadora?

Durante la instalación, ash refuerza el directorio ~/.ash con permisos exclusivos del propietario y los archivos administrados con permisos legibles y de escritura por el propietario. Esto protege contra otras cuentas locales bajo permisos normales de Unix, pero no contra su propia cuenta, administradores, copias de seguridad o software que elija ejecutar con acceso a su directorio personal.

Herramientas y flujo de trabajo

¿ash admite tuberías y otras tradiciones de Unix?

Sí. Puede canalizar texto en ash como mensaje, por ejemplo git diff | ash. Para las canalizaciones de herramientas solicitadas por IA, ash admite de dos a dieciséis ejecutables incluidos en la lista permitida y conectados directamente sin un shell, como ls | grep pattern | pbcopy. Los patrones de control de shell en los argumentos de la herramienta están bloqueados y todos los ejecutables en una canalización administrada por ash deben estar incluidos en la lista de permitidos.

¿Reinterpretará ash los comandos dentro de mis scripts de shell, comandos SSH o trabajos cron?

No. Los contenedores de integración Bash y zsh regresan inmediatamente en shells no interactivos, por lo que los scripts, los trabajos de CI, las frases ingeniosas de SSH y los comandos cron mantienen el comportamiento normal de comando no encontrado. Utilice una invocación explícita como ash "summarize this log" o some-command | ash cuando la automatización debería llamar a ash.

¿Cómo puedo evitar que ash interprete mis comandos durante unos minutos?

Ejecute ash snooze durante los cinco minutos predeterminados o especifique una duración como ash snooze 30s o ash snooze 1h. Ejecute ash snooze off para reanudar inmediatamente. Snooze pausa el enrutamiento automático de comandos no encontrados y de envoltura; Los comandos ash ... explícitos aún funcionan.

¿Cómo puedo depurar ash y ver más información sobre lo que está haciendo?

Configure ASH_VERBOSE=1 antes de ejecutar ash para habilitar la salida de depuración estructurada y un panel de ejecución de terminal. Configure ASH_LOG_FILE para escribir JSON de depuración en un archivo; ASH_LOG_MAX_BYTES controla la rotación y el valor predeterminado es 1 MiB cuando se configura un archivo de registro.

¿Qué límites se aplican cuando ash ejecuta herramientas?

De forma predeterminada, cada llamada de herramienta tiene un tiempo de espera de 15 segundos y captura hasta 8192 bytes de salida. Una solicitud de IA puede realizar hasta 16 iteraciones de bucle de herramientas, y una canalización administrada por ash tiene de dos a dieciséis etapas. Ajuste el tiempo de espera de la herramienta y el límite de salida con ASH_TOOL_TIMEOUT y ASH_TOOL_OUTPUT_MAX; mantenga la salida enfocada con comandos como head, tail o grep.

¿Dónde está el indicador predeterminado del sistema?

El archivo de solicitud canónico es ~/.ash/.ash_system, y se instala desde el paquete predeterminado cuando ejecuta ash install. ash lee ese archivo primero. Si está ausente, ash vuelve a .ash_system en el directorio de trabajo actual y luego a ~/.ash_system. Los valores $VARIABLE ordinarios se expanden desde el entorno, pero $TOOLS_DIR_LIST, $PLUGINS_DIR_LIST y $IF_PYTHON_AVAILABLE son sustituciones internas reservadas de Ash y nunca se derivan del entorno.

¿Dónde coloco mis propios scripts y complementos nativos? ash para llamar como herramientas?

Coloque scripts de Python en ~/.ash/tools/ y complementos binarios nativos compilados en ~/.ash/plugins/. Asegúrese de que sean ejecutables y agregue el nombre del ejecutable simple a ~/.ash/.ash_allow (o confíe en $TOOLS_DIR_LIST / $PLUGINS_DIR_LIST). ash no invoca un shell para los comandos y complementos permitidos de Unix.

¿Cuáles son las mejores prácticas para una herramienta o complemento para que la IA comprenda su propósito y uso?

Siga el patrón estándar de herramienta/complemento: exponga opciones predecibles con argumentos CLI; e implementar una opción --ai-docs que explique las capacidades, cada argumento y valor predeterminado, el esquema de salida, los estados de falla y cuándo la IA debe usar la herramienta. Emita JSON estructurado compacto con un campo status y detalles de error procesables en lugar de prosa mezclada con datos. Mantenga la salida limitada, valide las entradas, establezca tiempos de espera de red, maneje las fallas esperadas y haga que la herramienta sea segura para llamar repetidamente. Agregue su nombre de archivo simple a ~/.ash/.ash_allow; ash puede ejecutarlo solo cuando está en la lista permitida y no en ~/.ash/.ash_deny.

¿Cuáles son los scripts de herramientas y complementos nativos proporcionados?

Los scripts de arranque de Python instalados son headlines.py, wikipedia.py y yfinance.py en ~/.ash/tools/. Los complementos nativos proporcionados son what_time_is_it (Go), flip_a_coin (Rust) y calculator (TypeScript) en ~/.ash/plugins/.

¿Puede ash llamar a subagentes?

Sí. Un agente principal puede utilizar run_sub_agent para una tarea independiente y centrada. Un hijo hereda el directorio de trabajo, la configuración, las herramientas y los permisos del sistema operativo, devuelve un resultado limitado y no puede crear otro hijo. El máximo predeterminado es seis subagentes por ejecución principal y se puede cambiar con ASH_MAX_AGENTS.

¿Puede ash generar archivos de memoria para realizar un seguimiento de tareas complejas y lo que ha aprendido en la sesión?

Sí. Puede escribir archivos de espacio de trabajo persistentes en ~/.ash, de los que se realiza un seguimiento en ~/.ash/inventory.md, y archivos temporales con ámbito de sesión en ~/.ash/scratch/<session-id>/. Utilice archivos de espacio de trabajo persistentes para la información que desea conservar; utilice archivos borrador para planes temporales, notas y artefactos auxiliares.

¿Puede ash programar el trabajo para más tarde?

Sí, a través de sus herramientas de inteligencia artificial. En macOS, la programación única utiliza un launchd LaunchAgent por usuario y requiere launchctl. En Linux, las programaciones recurrentes se admiten a través de su usuario crontab; ash gestiona sólo sus propias entradas marcadas. El programador único launchd no está disponible en Linux, así que use una entrada cron u otro programador de Linux para un trabajo de Linux único. Las ejecuciones programadas reciben un entorno limitado y utilizan HTTPS directo en lugar de un intermediario de shell interactivo, así que asegúrese de que la configuración de IA requerida esté disponible para el trabajo programado. No pueden utilizar herramientas MCP remotas; Ash se ejecuta sin ellos y no advierte en sesiones no interactivas. No programe mensajes que requieran MCP.

Sesiones y almacenamiento

¿Dónde están el historial o los archivos de registro de ash?

El historial de conversaciones se almacena como JSON en ~/.ash/history/<SESSION_ID>.json; las ejecuciones programadas utilizan task_<SESSION_ID>.json. Cuando el registro de depuración programado está habilitado, su ubicación de registro predeterminada es ~/.ash/logs/task_<SESSION_ID>.log. Puede elegir otra ruta de registro de depuración con ASH_LOG_FILE.

¿Durante cuánto tiempo se retienen los archivos históricos?

ash elimina los archivos JSON del historial con más de 14 días durante la limpieza normal de la aplicación, con un presupuesto de limpieza de 300 ms para que la salida no se retrase. La ventana de mensajes recientes está separada: mantiene hasta 40 mensajes por conversación de forma predeterminada y se puede cambiar con ASH_HISTORY_MAX.

¿Cómo borro una conversación o empiezo de nuevo?

El historial está separado por ID de sesión y clave de modelo/punto final de IA. Inicie una nueva sesión de terminal para una nueva ID de sesión o elimine el archivo JSON relevante en ~/.ash/history/ cuando desee descartar intencionalmente ese historial de conversaciones local. Eliminar un archivo de historial no revoca una clave de proveedor ni elimina datos del lado del proveedor; adminístrelos por separado con el proveedor.

¿Qué es SESSION_ID y dónde se genera?

Es el identificador por sesión que se utiliza para separar el historial, el espacio temporal, los sockets de intermediario y los nombres de registros programados. El entorno del shell administrado genera un valor alfanumérico aleatorio de 16 caracteres a partir de /dev/urandom cuando se inicia el shell; ash también crea uno cuando una invocación interactiva no tiene valor.

¿Puedo reemplazar la implementación del generador SESSION_ID?

Puede proporcionar su propio SESSION_ID antes de iniciar ash o personalizar su archivo de entorno administrado local, pero ash lo valida. Los ID válidos tienen como máximo 128 caracteres y utilizan letras, dígitos, guiones bajos y guiones, con un sufijo de punto opcional para la sesión secundaria. No utilice valores compartidos o que no sean de confianza: las colisiones combinan el historial de sesiones y el estado de ejecución.

Soporte y comunidad

¿Cómo presento un error?

Abra un problema en github.com/Jonconradt/ash/issues con la versión o confirmación ash, su sistema operativo y shell, la configuración relevante para el problema con secretos eliminados, pasos reproducibles y el resultado observado. Para una vulnerabilidad de seguridad, no abra una edición pública; infórmalo de forma privada por correo electrónico o aviso de seguridad de GitHub.

¿Hay un foro de discusión en el proyecto ash?

Sí. Utilice GitHub Discussions para preguntas e ideas, y GitHub Issues para errores reproducibles y seguimiento del trabajo.
